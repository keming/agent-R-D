# 三相变压器优化计算引擎加速工具 用户操作手册

> 版本：v1.0 | 适用系统：三相变压器优化设计模块 | 适用用户：设计工程师 / 报价工程师 / 系统管理员

## 一、产品概述

### 1.1 这是什么

三相变压器优化计算引擎加速工具是嵌入报价系统中的一组后台优化模块，它**自动且透明地**加速优化计算过程，同时保证计算结果与原始引擎完全一致。你几乎感觉不到它在工作——只是计算变快了、等待变短了。

### 1.2 核心功能

| 功能 | 作用 | 用户可见性 |
|------|------|-----------|
| **早起剪枝** | 提前淘汰不可能出 FULL 的参数组合，减少无效迭代 | 不可见（后台驱动） |
| **缓存复用** | 对重复出现的基础参数组合结果缓存重算 | 不可见（后台驱动） |
| **并行计算** | 利用多核 CPU 同时计算多个 CRGOD 候选值 | 不可见（后台驱动） |
| **加速效果看板** | 展示优化前后的性能指标对比 | ✅ 可见（看板） |

### 1.3 谁需要用这个手册

| 角色 | 阅读内容 |
|------|---------|
| **设计工程师** | 了解推荐系统的"幕后加速机制"，理解推荐结果为什么可信 |
| **报价工程师** | 关注加速后的计算周期，快速响应客户 |
| **系统管理员** | 查看加速效果看板、维护缓存、处理异常降级 |

## 三、功能详解

### 3.1 早起剪枝（默认开启，无需配置）

#### 机制说明

计算引擎在 10 层嵌套循环中，先算"最容易淘汰"的约束条件（磁通密度 CT、高度限制）。如果第 2 层循环就算出磁通密度的初步值超出允许范围，就直接跳到下一个候选，**不再进入内层 8 层循环**。

可以类比为：面试候选人时，先看简历的硬筛选条件——学历不符的话直接跳过，不用笔试面试全部走一遍。

#### 查看剪枝效果

加速效果看板 → "早起剪枝"面板：

```
当前剪枝策略：活跃
历史记录中 CT 超限占比：32%
平均每方案提前跳过的内层循环数：4,200 次
```
### 3.2 缓存复用（默认开启，无需配置）

#### 机制说明

系统自动缓存以(硅钢片牌号, 铁心直径, 低压匝数)为 Key 的中间计算结果。当同样的参数组合在不同方案中再次出现时，直接从缓存读取，不再重复计算。

#### 查看缓存命中率

加速效果看板 → "缓存"面板：

```
缓存容量：20,000 条
命中率：23%
缓存命中节省的计算时间：约 15 分钟/百次计算
最近 10 分钟命中次数：142 次
最热 Key：(B30P105, 370, 12) — 命中 8 次
```

当缓存命中率低于 5% 时，系统会自动报告"缓存收益低"，管理员可选择关闭缓存。

### 3.3 并行计算（默认开启，可手动降级）

#### 机制说明

系统自动将 CRGOD（铁心直径）维度的计算拆分到多个 CPU 线程上并行执行。比如铁心直径设了 [350, 360, 370, 380, 390] 五个候选值，在 4 核 CPU 上同时算 4 个，算完再算第 5 个——理论加速 ≈ 3-4x。

#### 手动关闭并行（降级）

当并行执行出现异常或调试问题时，管理员可关闭并行模式：

1. 进入 **系统管理 → 引擎配置**
2. 找到 **并行计算** 开关
3. 设为 **关闭**
4. 系统自动回退到单线程模式，计算结果不变，只是慢一些

```
⚠️ 注意：关闭并行后计算时间会增长 3-5 倍。
建议只在排查问题时临时关闭，排查完后重新开启。
```

### 3.4 加速效果看板（系统管理员专用）

#### 入口

## 四、常见问题（FAQ）

### Q1: 加速后的计算结果和原来一样吗？

**完全一样。** 加速方案只改变了计算路径或利用了硬件资源——早起剪枝只是调整了 reject 的顺序，缓存只是复用中间结果，并行只是拆开同时算。物理公式、验证逻辑、输出结果与原始引擎完全一致。你可以任意抽查：同一方案在加速引擎和原始引擎上跑一次，结果 100% 相同。

### Q2: 加速引擎会不会漏掉最优解？

早起剪枝不会——因为它使用与原始引擎相同的物理约束条件来 reject，只是把它提前了。如果某个组合在原始引擎中最终会算出 FULL 结果，它在加速引擎中同样不会被 reject。

并行计算不会——因为只是把计算拆到不同线程，每线程内算的和单线程一样。

缓存不会——缓存的 Key 设计确保只有完全相同的基础参数组合才命中，不会用近似值替代精确计算。

**唯一需要关注的情况**：如果未来引入分步优化（先固定铁心参数再优化绕组），需要额外验证不遗漏解。届时会出专门的验证报告。

### Q3: 为什么加速后计算时间还是不稳定？

这是正常的。计算时间受以下因素影响：

- **方案复杂度**：大容量（10MVA+）方案的计算量是小容量（500kVA）的 5-10 倍
- **推荐范围宽窄**：推荐的搜索范围如果较宽（广泛策略），计算时间会长于精准策略
- **缓存预热状态**：新软件刚上线时空缓存，跑几天后命中率会逐渐提升
- **服务器负载**：同时提交多个方案时，CPU 资源竞争

### Q4: 怎么知道加速工具有没有在工作？

不需要主动确认。当你的方案计算结果比预期快了很多——嗯，它已经在工作了。

如果一定要看确认证据：
1. 打开加速效果看板
2. 看"总览"面板的实时加速比 > 1.0x

### Q5: 缓存命中率低怎么办？

缓存命中率受参数组合的重复程度影响。如果每个方案的铁心直径、硅钢片牌号组合都不同，命中率确实会低。这不代表系统有问题——只是说明你的方案多样性高。如果命中率持续低于 5%，管理员可关闭缓存层（系统管理 → 引擎配置）。

### Q6: 并行计算报错了怎么办？

1. 检查服务器 CPU 核数是否 ≥2（单核系统不支持并行）
2. 进入系统管理 → 引擎配置，关闭并行开关
3. 联系系统管理员排查报错信息

### Q7: 升级引擎后，参数推荐系统需要重算权重吗？

不需要。参数推荐系统（param-recommendation）与引擎加速是**完全独立**的两个模块。推荐系统只依赖历史 FULL 记录的数据分布，不依赖引擎的计算路径。加速引擎跑出的 FULL 记录仍然会自动进入推荐系统的训练数据。

维护建议：建议每月重算一次推荐权重（通过"权重管理"→"重新计算"），但与引擎加速无关。

## 五、日常运维任务

### 5.1 每日检查（1 分钟）

```
□ 打开加速效果看板
□ 确认加速比 ≥ 1.5x（如果 < 1.5x 可能配置有问题）
□ 确认无异常报错
```

### 5.2 每周检查（5 分钟）

```
□ 查看缓存命中率趋势
   □ 如果连续 3 天 < 5%，评估是否关闭缓存
   □ 如果连续 3 天 > 30%，不需干预
□ 查看并行任务失败率
   □ 如果 > 1%，检查服务器资源
```

### 5.3 月度维护（10 分钟）

```
□ 查看过去 30 天加速比趋势图
   □ 如果加速比持续下降，重新评估推荐系统权重
□ 审查引擎优化日志（系统管理 → 引擎日志）
   □ 确认无异常 warning
□ 备份当前引擎配置快照
```

## 六、故障处理

| 现象 | 可能原因 | 处理步骤 |
|------|---------|---------|
| 加速比 < 1.2x | 并行未生效 / 缓存命中率极低 | ① 检查并行开关 ② 检查 CPU 核数 ③ 检查缓存命中率 |
| 计算时间反而变长 | 并行降级后 CPU 资源充足但串行执行 | ① 检查是否有线程安全回退 ② 重启引擎服务 |
| 缓存占用内存过高 | 缓存容量设置过大 | 调整最大缓存条目数（默认 20000 → 10000） |
| 并行计算失败率高 | 共享状态未正确加锁 | ① 关闭并行降级 ② 联系开发人员审查代码 |
| 早起剪枝返回空结果（无方案通过） | 剪枝策略过于激进 | 回退到上一版剪枝配置（备份自动保留 3 个版本） |

## 八、技术参考（系统管理员）

### 8.1 配置参数

| 参数 | 默认值 | 说明 | 修改位置 |
|------|--------|------|---------|
| `engine.parallel.enabled` | true | 是否启用并行计算 | 系统管理 → 引擎配置 |
| `engine.parallel.threads` | auto（= CPU 核数 - 1） | 并行线程数 | 系统管理 → 引擎配置 |
| `engine.cache.enabled` | true | 是否启用缓存 | 系统管理 → 引擎配置 |
| `engine.cache.maxSize` | 20000 | 最大缓存条目数 | 系统管理 → 引擎配置 |
| `engine.pruning.enabled` | true | 是否启用早起剪枝 | 系统管理 → 引擎配置 |
