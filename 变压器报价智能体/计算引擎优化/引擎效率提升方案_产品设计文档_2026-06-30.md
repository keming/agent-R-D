## Phase 1: DISCOVER — 我们要解决什么问题？

### 1.1 问题陈述

三相变压器优化计算的 10 层嵌套循环结构中，超过 99% 的 `calculate()` 迭代产出非 FULL 结果。每次调用执行 1000 多行物理公式代码，搜索空间可达 10^16 量级。当报价工程师需要快速响应客户询价时，单方案计算耗时以小时计，严重影响报价效率和客户体验。

**量化损失：**

| 指标 | 当前值 | 目标值 | 改进空间 |
|------|--------|--------|---------|
| 单方案迭代次数 | 10^6~10^16 | ≤10^5 | 99%+ |
| 单方案计算时间 | 0.5~5 小时 | ≤10 分钟 | 90%+ |
| 单次报价周期 | 1~3 天 | ≤4 小时 | 80%+ |
| 计算集群每日方案数 | 5~10 个 | 50~100 个 | 10x |

### 1.2 多视角脑暴

| 视角 | 观点 | 关键洞察 |
|------|------|---------|
| **产品经理** | 问题在搜索范围过大，而不是引擎慢 | 99% 的迭代是浪费的 → 优先减少无效迭代，其次加速有效迭代 |
| **设计师** | 用户（工程师）无法直观看到"在哪里浪费" | 如果能把搜过的空间和跳过的空间可视化，工程师会更信任推荐 |
| **工程师** | 引擎代码耦合度高，任何改动都有风险 | 需要可逆的优化方案，收益不确定的改动优先级靠后 |

**Top 5 入选想法：**

1. **早起剪枝** — 将淘汰率最高的约束提前到外层（A 方案）——零风险，收益确定
2. **缓存复用** — 中间结果缓存重算（B 方案）——零行为变化
3. **外循环并行** — CRGOD 维度并行化（E 方案）——与推荐系统正交
4. **热区编译优化** — 热点方法内联 + 对象池 + Vector API（F 方案）
5. **分步解耦** — 铁心参数先固定，再优化绕组（C 方案）——收益大但需验证

### 1.3 假设识别（8 类风险）

| # | 风险类别 | 假设 | 验证状态 |
|---|---------|------|---------|
| 1 | 💡 价值风险 | 早起剪枝能在不遗漏解的前提下加速 ≥30% | ❌ 未验证（需统计 reject 原因） |
| 2 | 💡 价值风险 | 缓存命中率 ≥20%（非极低重复场景） | ❌ 未验证（需做 heat map 分析） |
| 3 | 🎯 可用性风险 | 引擎开发团队能理解并行化后的线程安全模型 | ✅ 已验证（有 Java 并发经验） |
| 4 | ⚙️ 可行性风险 | 分步优化（C 方案）能证明不遗漏全局最优 | ❌ 未验证（核心风险） |
| 5 | ⚙️ 可行性风险 | 并行化后共享状态改造量可控 | ❌ 未验证（需代码审查） |
| 6 | 💰 商业风险 | 加速计算可转化为报价周期缩短，提升订单转化 | ✅ 已验证（业务逻辑成立） |
| 7 | 🧑‍🤝‍🧑 团队风险 | 引擎开发有 1-2 人力投入 2-8 周 | ✅ 已验证（团队排期可行） |
| 8 | 📊 GTM 风险 | 用户（设计工程师）愿意采纳推荐范围 | ✅ 已验证（已在使用中） |
| 9 | 🎯 战略风险 | 引擎优化与推荐系统（param-recommendation）方向一致 | ✅ 已验证（完全正交，可叠加） |
| 10 | 🧪 伦理风险 | 优化不改变计算结果，不引入偏差 | ✅ 已验证（A/F/B 不改变逻辑） |

### 1.4 优先级矩阵

```
              高风险
                │
                │  C 分步优化
                │  E 并行化（线程安全风险）
                │
    低影响 ────┼──── 高影响
                │
                │  A 早起剪枝 ★
                │  B 缓存 ★
                │  F 编译优化
                │
              低风险
```

- **🔥 高优先级**：A（早起剪枝）、B（缓存）— 高风险低，实施快
- **🔵 中优先级**：E（并行化）、F（编译优化）— 收益明确但需要额外验证
- **⚠️ 需验证**：C（分步优化）— 收益高但风险大

### 1.5 低成本实验

| # | 假设 | 实验 | 期望输出 | 成本 |
|---|------|------|---------|------|
| 1 | reject 原因可预测 | 统计 500 条历史 FULL 记录和 reject 日志，分类 | reject 分布直方图 | 0.5 天 |
| 2 | 缓存命中率 ≥20% | 分析 1000 条计算记录的参数重复率 | 重复组合热力图 | 0.5 天 |
| 3 | 并行化改造量可控 | 代码审查 calculate() 中的共享变量 | 共享变量清单 + 改造预估 | 1 天 |

## Phase 2: RESEARCH — 谁在使用？市场什么样？

### 2.1 用户画像

#### 画像 A：设计工程师（核心用户）

| 维度 | 内容 |
|------|------|
| **身份** | 变压器设计工程师，3-10 年经验 |
| **痛点** | 每次新建方案要手动设置优化范围；等计算结果耗时；不确定范围设得是否合理 |
| **JTBD** | "当我要新建报价方案时，我想快速得到参数推荐范围，这样就能减少无效计算等待时间" |
| **3 大痛苦** | (1) 手动设范围靠经验，新手常出错；(2) 等计算结果动辄 1 小时以上；(3) 不同容量/电压方案的推荐经验难复制 |
| **3 大收益** | (1) 10 分钟内出结果；(2) 推荐范围准确不遗漏；(3) 系统越用越准 |
| **反直觉洞察** | 设计工程师并不排斥"黑盒推荐"——只要最后一步仍然由计算引擎完成物理验证。他们排斥的是"跳过我的计算引擎直接给结果" |

#### 画像 B：报价工程师

| 维度 | 内容 |
|------|------|
| **身份** | 销售技术支持，快速响应客户询价 |
| **痛点** | 客户等报价太久，导致丢单 |
| **JTBD** | "当客户发来询价时，我想在 30 分钟内出初步方案和报价，这样就能提高中标率" |
| **核心诉求** | 越快越好，精度允许适当让步（快速近似方案） |

#### 画像 C：系统开发/运维

| 维度 | 内容 |
|------|------|
| **身份** | 平台开发/计算集群运维 |
| **痛点** | 计算引擎每次改代码都紧张；批量报价时集群满载 |
| **JTBD** | "当优化计算需求增加时，我想在不增加服务器的前提下提升吞吐量，这样就能控制成本" |

### 2.2 工作故事（Job Stories）

| # | 场景 | 故事 |
|---|------|------|
| 1 | 新建方案 | "当我要新建一个三相方案时，我想让系统自动推荐优化参数范围，这样就不用凭经验手动设了" |
| 2 | 等待计算 | "当我提交方案等待计算结果时，我想知道什么时候能出结果、为什么这么慢，这样就能安排我的工作计划" |
| 3 | 批量报价 | "当我需要同时出多个方案报价时，我想让计算快速完成，这样就不会因为等待时间太长而丢单" |
| 4 | 系统维护 | "当我需要修改引擎代码时，我想确保改动不会破坏现有方案的正确性，这样我就不必逐一验证" |
| 5 | 用户培训 | "当新同事刚接触系统时，我想让他理解推荐范围的原理和可信度，这样他就能正确使用而非全部采纳" |

### 2.3 竞品分析

| 竞品/替代方案 | 方法 | 优点 | 缺点 | 差异化机会 |
|-------------|------|------|------|-----------|
| **手工设范围**（当前方案） | 工程师凭经验设定 | 灵活 | 依赖经验，新人上手慢 | 推荐系统替代人工经验 |
| **ANSYS Maxwell 优化** | 遗传算法 + 参数化扫描 | 自动化强、可视化好 | 价格高（10万+/年）、部署重 | 轻量级内嵌方案，随报价系统交付 |
| **Altair HyperStudy** | DOE + 响应面 + 优化 | 支持多目标 | 学习成本高、与现有引擎集成难 | 与自有引擎深度集成，零壁垒 |
| **穷举全量搜索**（旧方案） | 遍历所有组合 | 不遗漏解 | 时间成本不可接受 | 不做——推荐+搜索缩小才是方向 |
| **第三方报价软件**（如 Transformer Design Pro） | 自带优化引擎 | 开箱即用 | 不支持定制化线规/材料 | 自有引擎+自学习，越用越准 |

**差异化定位**：不替代计算引擎，不改变物理逻辑，不做预测——只做"缩小入口"，与现有系统零侵入集成。

### 2.5 机会-方案树（OST）

```
可衡量结果：单方案计算时间从小时级降到 ≤10 分钟
  │
  ├── 机会 1：外层循环浪费大量算力（99%+ 无效迭代）
  │     ├── 方案 1a ★ 早起剪枝（A）：将 CT 验证提到内层，提前 reject
  │     ├── 方案 1b 缓存复用（B）：相同参数组合的中间结果缓存
  │     └── 方案 1c 推荐缩小范围（已有）：param-recommendation
  │
  ├── 机会 2：多核 CPU 未充分利用
  │     └── 方案 2a ★ 外循环并行（E）：ForkJoinPool 拆分 CRGOD 维
  │
  ├── 机会 3：引擎代码微观效率不足
  │     ├── 方案 3a ★ 热点内联（F）：JProfiler 定位 + 手动内联
  │     └── 方案 3b 对象池化（F）：calculate() 内临时对象复用
  │
  └── 机会 4：搜索空间可结构化拆分
        └── 方案 4a 分步优化（C）：铁心参数→绕组参数→油箱，三阶段
```

| # | 部分 | 内容 |
|---|------|------|

### 4.1 北极星指标

**游戏类型**：Productivity Game（帮用户高效完成报价方案计算）

**北极星指标**：**单方案 FULL 级计算时间（分钟）**

**输入指标**：

| 输入指标 | 说明 | 当前值 | 目标值 |
|---------|------|--------|--------|
| 每次 calculate() 平均耗时 | 单位调用微优化 | 1000 行代码/调用 | 减少 20-50% |
| 每次方案迭代总次数 | 缩小搜索空间 + 早起剪枝 | 10^6~10^16 | ≤10^5 |
| 推荐覆盖率 | 推荐范围包含真实最优的比例 | 80-90% | ≥95% |
| 缓存命中率 | 中间结果复用比例 | 未知 | ≥20% |

### 4.2 OKR

**O1：大幅缩短单方案计算时间**
- KR1.1：Phase 1 交付后，有 FULL 历史记录的方案平均计算时间从小时级降至 ≤30 分钟
- KR1.2：Phase 2 交付后，降至 ≤10 分钟
- KR1.3：总迭代次数减少 ≥80%

**O2：优化可量化、结果可验证**
- KR2.1：每次引擎改动后有回测覆盖率对比（新旧权重 → 验证不损失解）
- KR2.2：建立 reject 原因统计看板，持续跟踪剪枝效果
- KR2.3：缓存命中率监控上线

**O3：零业务影响**
- KR3.1：所有优化方案的物理计算结果与原始引擎完全一致
- KR3.2：无一期因引擎优化导致计算 Bug 回退
- KR3.3：并行化后单线程模式（降级）与并行模式结果一致

## Phase 5: EXECUTE — 把它做出来

### 5.1 Pre-Mortem

假设引擎优化上线 14 天后彻底失败了——

| 失败原因 | 类型 | 概率 | 影响 | 行动 |
|---------|------|------|------|------|
| **早起剪枝导致丢解**——把 CT 提到第 2 层后，某些方案在第 2 层的 CT 临时值超出范围被 reject，但第 9 层优化后可在范围内 | 🐅 Tiger | 中 | 高 | 设计 kill criteria：回测覆盖率降低 ≥5% 时自动告警，回退到原顺序 |
| **缓存命中率不到 5%**——每个方案的参数组合都不同，缓存几乎不命中 | 📄 Paper Tiger | 高 | 低 | 缓存只加不加锁就 0 风险，不命中只浪费少许空间，无副作用 |
| **并行化后线程安全问题导致竞态**——共享变量未加锁，结果不稳定 | 🐅 Tiger | 中 | 高 | 代码审查清单必检共享变量；先单线程跑验证，再并行跑 |
| **分步优化遗漏全局最优**——铁心参数先固定 → 绕组参数后优化，漏掉了"非最优铁心+最优绕组"的组合 | 🐘 Elephant | 低 | 致命 | 不做硬分步，改为"软分步"：先推荐引导，仍然穷举兜底 |
| **团队产能不足**——其他项目优先级更高，引擎优化做了一半就停了 | 🐘 Elephant | 中 | 中 | Phase 1（2 周）设为首要优先级——先拿到 50% 加速 |

**Kill Criteria：**
1. 早起剪枝后回测覆盖率降低 ≥5% → 回退，改为更保守的剪枝策略
2. 并行化后对比单线程结果不一致 → 排查线程安全，修复前保持单线程
3. 缓存命中率连续观测 1 周低于 5% → 移除缓存层

### 5.2 Red Team（攻击载荷假设）

| # | 假设 | 攻击问题 | 最便宜验证 | Kill Criteria |
|---|------|---------|-----------|-------------|
| 1 | "把 CT 提到第 2 层不会丢解" | 如果某个方案的 CT 在第 2 层算出来超出范围，但第 9 层优化绕组后 CT 降低了，怎么办？ | 在历史 FULL 记录中反查——CT 在最外层就超限但最终 FULL 的记录有多少？ | ≥5% 的历史记录因此被误杀 |
| 2 | "外循环并行后结果一致" | 共享变量在并发下产生不同的计算结果？ | 代码 review + 1 万次并行/单线程结果对比 | 任意一次结果不一致 |
| 3 | "缓存命中率足够高" | 如果每个方案的参数组合都是唯一的，缓存是否白加了？ | 分析 1000 条记录中参数组合的重复率 | 重复率 <5% |

### A.2 早起剪枝逻辑

```java
// 优化前：CT 在第 3 层之后才计算，约束在第 9 层才校验
for (LVT : lvtRange) {                    // 第 2 层
    for (CRGOD : crgodRange) {             // 第 3 层
        double ct = calcCT(crgod, ...);    // 计算磁通密度
        for (线厚 : 线厚列表) {              // 第 4-9 层
            // ... 1000+ 行计算 ...
            if (ct超出范围 || 高度超出范围)  // 第 9 层校验，太晚了！
                reject();
        }
    }
}

// 优化后：CT 在第 2 层后立即校验
for (LVT : lvtRange) {                    // 第 2 层
    // ← 立即做 CT 初验（基于 LVT + 典型 CRGOD 估算）
    double ct_est = estimateCT(lvt);
    if (ct_est超出范围) continue;          // 提前跳过全部内层！
    
    for (CRGOD : crgodRange) {             // 第 3 层
        double ct = calcCT(crgod, lvt);    // 精确计算
        if (ct超出范围) continue;           // 提前跳过 4-10 层！
        
        for (线厚 : 线厚列表) {              // 第 4-9 层
            // ... 计算 ...
        }
    }
}
```
