# 三相变压器优化计算引擎效率提升方案对比

> 日期：2026-06-30 | 作者：陈科明

## 一、背景

当前计算引擎的核心问题是**搜索空间过大**。10 层嵌套循环中超过 99% 的 `calculate()` 迭代产出无效结果（非 FULL），而每次 `calculate()` 调用执行 1000+ 行代码。当前系统已通过"参数推荐"（param-recommendation）缩小外层搜索范围来加速，但引擎本身的循环结构和计算路径未做优化。

本文从**引擎内部**（而非仅从搜索范围）出发，梳理所有可提升效率的方案。

---

## 二、方案对比总览

| 编号 | 方案 | 核心思路 | 预估效果 | 实现成本 | 风险 |
|------|------|----------|----------|----------|------|
| A | 循环重排序 + 早起剪枝 | 把最可能 reject 的约束提前检查 | 减少 30-50% 深层循环进入 | 低（1-2 人周） | 低 |
| B | 缓存命中检测（Memoization） | 相同中间结果缓存复用 | 减少 10-30% 重复计算 | 中（2-4 人周） | 低 |
| C | 参数独立性分析 + 分步优化 | 将 10 层拆成独立子问题，分步优化 | 减少 60-80% 迭代量 | 高（4-8 人周） | 中（可能漏全局最优） |
| D | 梯度引导搜索（局部搜索替代遍历） | 用局部搜索（如模拟退火）替代全遍历 | 将 10^16 → 10^4 量级 | 高（4-6 人周 + 算法调参） | 高（无法保证找到最优解） |
| E | 并行计算 | 多层循环并行化 | 理论加速 N 倍（N = CPU 核数） | 中（2-4 人周） | 中（竞态条件/线程安全） |
| F | 编译优化（AOT/JIT） | Java 代码 AOT 编译或循环内联优化 | 单次 calculate() 提速 20-50% | 低（1-2 人周，视 JVM 版本） | 低 |
| G | 整数规划建模 | 将物理约束转为 MILP 模型求解 | 理论上秒级 | 极高（4-12 人月） | 极高（建模困难，离散变量多） |

---

## 三、各方案详解

### A. 循环重排序 + 早起剪枝 ★ 高性价比推荐

#### 原理

当前 10 层循环的顺序可能不是最优的。将能早期 reject 方案的约束条件（如磁通密度、阻抗、温升）尽可能提前到外层循环检查，让无效组合在进入内层深循环前就提前退出。

#### 当前循环结构（示意）

```
1. 硅钢片牌号    ← 约束少
2. LVT（匝数）     ← 直接循环变量
3. CRGOD（铁心直径）← 直接循环变量，可计算 CT
4. 低压线厚
5. 低压线宽
6. 低压层数
7. 高压线厚
8. 高压线宽
9. 高压层数 + 绕线高度计算
10. 油箱参数
```

#### 优化后结构

```
1. 硅钢片牌号
2. CRGOD（铁心直径）→ 立即算 CT ← 若 CT 超限，跳过后续全部
3. LVT              → 计算匝比，初步验证
4. 高压层数         → 预估高度，若撑不下提前跳过
5-8. 线厚线宽（可并行）
9-10. 油箱参数
```

#### 优点
- **改动小**：不需要改物理公式，只调循环顺序
- **风险极低**：不改变计算结果，只改变到达结果的路径
- **可叠加**：与其他方案完全不冲突

#### 缺点
- 加速效果有限（30-50%），不能根本解决搜索空间问题
- 需要深入理解每层循环物理约束的"淘汰率"，不同方案约束不同

#### 实施建议

对历史 FULL 数据的 reject 原因做统计，找出**淘汰率最高**的约束条件，把对应的计算步骤提到最早。

---

### B. 缓存命中检测（Memoization）★ 高性价比推荐

#### 原理

10 层嵌套循环中，大量子组合是重复的。例如：同一组"铁心直径 + 匝数 + 线厚线宽"组合在不同"导线规格"下可能重复出现。用哈希表缓存已经算过的中间结果，命中直接复用。

#### 缓存维度

| 缓存层 | Key | Value | 预期命中率 |
|--------|-----|-------|----------|
| 铁心参数缓存 | (硅钢片牌号, CRGOD) | 磁通密度、空载损耗 | 极高（多次共享） |
| 绕组缓存 | (LVT, 线厚, 线宽, 层数) | 窗口尺寸、填充率 | 高 |
| 温升缓存 | (绕组结构, 油道参数) | 温升估算值 | 中 |

#### 优点
- **零业务风险**：纯计算级优化，不改变逻辑
- 对重复子场景效果显著（同一参数组合不同油箱配置时）
- 实现成本低：Guava Cache / Caffeine 即可

#### 缺点
- 依赖重复率——如果每条记录的参数组合都不同，命中率低
- 缓存粒度需要权衡：粒度过细则 key 太多命中率低；粒度过粗则 value 太大内存开销高
- 多线程场景需要处理缓存一致性

---

### C. 参数独立性分析 + 分步优化

#### 原理

分析 10 层参数之间的**依赖关系图**，找出哪些参数可以独立优化。如果部分参数的取值不影响其他参数的优化路径，就将它们独立出来先固定，减少嵌套层次。

#### 分析结果（预期）

```
依赖性分析：
  铁心直径 CRGOD  → 直接影响 CT、空载损耗
                   → 不直接依赖线厚线宽
  低压匝数 LVT    → 影响匝比、铜耗
                   → 与线厚线宽弱耦合
  线厚线宽层数    → 只影响窗口填充和温升
                   → 与油箱参数较强耦合
  油箱参数        → 只影响散热、油重
                   → 与其他参数弱耦合
```

#### 分步方案

```
Step 1: 约束 CRGOD + LVT + CT（铁心参数）→ 筛选候选集 A
Step 2: 约束线厚线宽层数（绕组参数）→ 筛选候选集 B（可并行）
Step 3: A × B 组合验证温升、阻抗 → 输出 FULL
```

#### 优点
- 将 10 层嵌套降为 3 阶段 × 各阶段候选集缩小，理论迭代量骤降 60-80%
- 各阶段可以并行跑（如 Step 2 中不同线圈子方案并行）
- 分步出的中间结果在大规模报价业务中可复用

#### 缺点
- **风险**：参数间的弱耦合不是完全独立的，分步优化可能错过"看似不合理但搭配在一起刚好 PASS"的组合
- 物理验证难度大：需要证明分步不损失全局最优解，否则用户无法接受
- 实现成本高，需要重构 calculate() 的调用链

---

### D. 梯度引导搜索（局部搜索替代遍历）

#### 原理

用局部搜索算法（遗传/模拟退火/粒子群）替代全量穷举。初始猜测一个参数组合 → 计算目标值 → 局部微调 → 迭代收敛。

#### 适合当前场景的搜索算法对比

| 算法 | 适用场景 | 收敛速度 | 全局最优保证 | 实现难度 |
|------|----------|----------|-------------|----------|
| 模拟退火 | 离散参数多、目标函数连续 | 中 | 概率性（理论保证无限时间） | 低 |
| 遗传算法 | 组合优化 | 慢 | 概率性 | 中 |
| 贝叶斯优化 | 每次评估昂贵 | 快（样本高效） | 概率性 | 高 |
| 爬山法 | 单峰目标函数 | 极快 | 无（本地最优） | 低 |

#### 优点
- 理论上将 10^16 搜索空间降到 10^4 量级，数量级飞跃
- 可以和其他策略叠加（先用推荐缩小范围，再用搜索替代遍历）

#### 缺点
- **致命问题**：无法保证找到全局最优解。对于变压器设计这种"错过一个更优值可能丢掉订单"的业务场景，概率性算法风险极高
- 调参困难：不同容量/电压等级的最佳搜索参数差异大
- 用户信任问题：工程师习惯看到"找了所有组合，这个最好"的确信感，而非"算法认为这个好"
- 如果被 reject 条件卡住（无合法解），算法无法区分"搜索不够深"和"真的没有解"

---

### E. 并行计算

#### 原理

将 10 层循环中互不依赖的部分拆开并行，利用多核 CPU 或 GPU 加速。

#### 并行维度

| 方式 | 粒度 | 加速比上限 | 实现难度 |
|------|------|-----------|----------|
| 外层循环并行（如 CRGOD 各值并行） | 粗 | 4-8x（CPU 核数） | 低 |
| 内层循环并行（线厚×线宽展开） | 细 | 4-8x | 中 |
| GPU 计算（批量 evaluate） | 极细 | 10-100x | 极高 |

#### 优点
- 确定性加速——不改变计算结果的情况下，理论加速 = CPU 核数
- 外层循环并行最容易实现（CRGOD 各候选值无依赖）
- 与推荐系统正交，叠加使用效果更好

#### 缺点
- 当前架构若未考虑线程安全，大量共享变量需要改写
- GPU 方案需要把核心计算（1000+ 行）迁移到 CUDA/OpenCL，且 GPU 擅长的是 SIMD 而不是分支密集型逻辑——当前的物理公式含大量条件分支，GPU 效率反而低
- 并行只缩短墙钟时间，总计算量不变

---

### F. 编译优化（AOT/JIT）

#### 原理

Java 层面的微优化：热点代码预编译、循环内联、数值计算加速（Vector API）。

#### 可优化点

| 优化项 | 预期收益 | 做法 |
|--------|----------|------|
| 循环内联 | 5-15% | 消除方法调用开销 |
| 数值计算热点提取 | 10-20% | 将矩阵/向量运算改为 System.arraycopy 或 Vector API |
| AOT 编译（GraalVM） | 10-15% | 启动后无需 JIT warm-up |
| 对象池化 | 5-10% | 减少 calculate() 内的临时对象分配/GC |

#### 优点
- 纯工程优化，零业务风险
- 改动极小，逐个优化点独立推进

#### 缺点
- 收益上限明确：单次 calculate() 加速 20-50%，但内核的循环次数没变
- 随着硬件升级，收益递减
- GraalVM AOT 需要额外的构建/部署适配

---

### G. 整数规划建模（MILP）

#### 原理

将物理公式和约束条件线性化/凸化，用 MILP 求解器（Gurobi/CPLEX）一次求解最优参数组合。

#### 优点
- 理论上的最优解——求解器保证全局最优
- 求解速度极快（秒级到分钟级）

#### 缺点
- **几乎不可行**：变压器物理公式是非线性的（含乘积/除法/平方/饱和曲线），线性化误差不可控
- 离散变量极多（线规选择、层数整数、油道组合），MILP 求解规模会爆炸
- 需要重写全部物理公式为约束表达式，工作量等于重写整个计算引擎
- 求解器成本（Gurobi 商业许可很贵，且硬件要求高）

---

## 四、推荐组合方案

基于当前系统状态（已有推荐系统缩小外层范围），从性价比和实施可行性出发，推荐按以下优先级推进：

### 第一阶段：零风险优化（1-2 周）

```
A + B + F 组合
├─ A: 循环重排序 + 早起剪枝
│    → 统计历史 reject 原因，把淘汰率最高的 CT 验证提到第 1 层
│    → 预期：减少 30% 进入深循环
├─ B: 缓存命中检测
│    → CRGOD+牌号缓存、绕组结构缓存
│    → 预期：减少 15-20% 重复计算
└─ F: 编译优化
     → 热点方法内联、临时对象池化
     → 预期：单次 calculate() 提速 15%
```

**综合预期效果**：计算时间缩短 **50-65%**，零业务风险。

### 第二阶段：并行化（2-4 周）

```
E: 外层循环并行（CRGOD 维度）
├─ 改 CRGOD 循环为 ForkJoinPool 并行
├─ 需要确保 shared state 线程安全
└─ 预期：额外加速 3-5x（按 CPU 核数）
```

**综合预期效果**：计算时间缩短 **80-90%**（含第一阶段）。

### 第三阶段：架构级优化（如果需要）

```
C: 分步优化
├─ 风险较高，需要充分验证不遗漏全局最优
├─ 需要与设计工程师协作确认物理可行性
└─ 仅在前两阶段仍不够时才考虑
```

**D（梯度引导搜索）和 G（MILP）不建议在当前阶段采用**——前者无法保证最优解，后者工程成本远超收益且线性化误差难以控制。

---

## 五、效果预估汇总

| 阶段 | 方案 | 预估加速 | 风险等级 | 实施周期 |
|------|------|----------|----------|----------|
| 1 | A+B+F | 50-65% | 低 | 1-2 周 |
| 2 | +E | 80-90% | 中 | 2-4 周 |
| 3 | +C | 95%+ | 中高 | 4-8 周 |
| — | D（局部搜索） | 99%+ | 高 | 4-6 周 |
| — | G（MILP） | 99.9%+ | 极高 | 4-12 月 |

> **结论**：第一阶段（A+B+F）以最⻓ 2 周、零业务风险的代价，预期可将计算时间缩短一半以上，性价比最高。如果仍不够，第二阶段加并行可再叠加 3-5x 加速。
