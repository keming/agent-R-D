## 三、需要修正的问题

### 问题 1（严重）：第二类与现有参数推荐系统重复

你写的第二类方案：
```
查 ThreePhaseSchemeRecord，同容量±15%、同电压等级、同联结组别的历史记录
取 P5~P95 分位数，向外扩 15% 安全余量
```

而我们团队已经在生产中的 `param-recommendation` 模块已有的能力：

| 维度 | 你的方案 | 现有系统 |
|------|---------|---------|
| 输入特征 | 5 个手工规则（容量、电压、联结、线规、铁心形式） | 22 维（含油道、并绕方式、绕制系数等） |
| 匹配机制 | 同容量±15% + 同电压等级 | 4 硬门槛 + 加权相似度 |
| 权重方法 | 无 | 方差归约（Variance Reduction）+ 回测 |
| 推荐输出 | 一组 P5~P95 +15% 余量 | 三策略（精准/标准/广泛） |
| 用户交互 | 前端弹窗确认 | 前端弹窗 + 权重版本管理 + 回测对比 |
| 版本管理 | 无 | 版本号 + is_active 切换 |

**你在用一个 5 特征的规则版去复现一个已经跑通的 22 维统计学习系统**。这不是方向不对，是不了解已有积累。建议你：

1. 先去读 `param-recommendation-design-how.md` 了解现有设计
2. 把精力集中在第三类（计算顺序调整）和第一类（UK 粗估）上——这是现有方案没有覆盖的空白
3. 如果你仍然想做"范围推荐"的改进，方向应该是：**现有推荐系统覆盖了外层 5 个参数（CRGOD/LVT/LVRH/HVRH/CT），但内层线厚/线宽的推荐尚未实现，即设计文档中的 v2 方向。这才是你可以发力且有增量价值的地方。**

### 问题 2（重要）：UK 粗估公式的系数来源未交代

你的粗估公式：
```
LEAX = 3.95 × NI × 粗估漏抗面积 × HZ × 1.03 / (HK × 10 × ET × 5000000)
```

我需要你看清楚以下三个问题：

- **`3.95` 是什么？** 如果是经验系数，来源是什么？哪本教科书、哪个标准？
- **`1.03` 是安全系数还是其他物理量？**
- **分母的 `10` 和 `5000000`** ——单位换算逻辑是什么？
- **最关键**：你声称粗估 LeAX **系统偏小**（从而 UK 粗估偏小、只淘汰超上限的），这个结论有验证吗？拿 N 条历史 FULL 记录跑一遍，粗估 UK 和精确 UK 的真实分布是什么样的？

**要求**：给我两个东西——系数来源的引用（哪怕是工程经验手册的页码），以及粗估 vs 精确的偏差分布统计（50 条以上历史记录）。

### 问题 3（重要）：缺少验证方案

你写的是「用已有历史方案参数重算验证」，但这个太模糊。一个可执行的验证计划至少需要：

- **验证集**：选多少条？随机抽取还是覆盖所有电压等级/容量等级？
- **通过率**：粗估 UK 前置后，预期淘汰多少方案？实际多少？
- **误杀率**：粗估 UK 未淘汰但精确 UK 可以通过的占比——必须为 0%，否则方案不成立
- **结果一致性**：代码整体改动后，P0/PK/UK/温升/成本与改动前偏差多少以内才算通过？建议 < 0.5%
- **测试条件**：在测试数据库还是 production 数据上跑？跑一次多少条？

**要求**：补一个验证计划文档（test plan），哪怕还没执行，写清楚上面这些判定标准。

### 问题 4（需补充）：未讨论与推荐系统的叠加效果

现有的 `param-recommendation` 做的优化维度：
- 外层循环入口缩小：CRGOD/LVT 等 5 个参数的推荐范围缩小 60-90%
- 效果：**进入 `calculate()` 的 WorkItem 总数大幅减少**

你的方案做的优化维度：
- 内部加速：每次 `calculate()` 内部通过阶段拆分 + 早判淘汰 20-30% 的无效迭代
- 效果：**单次 calculate() 的计算量减少**

这两个效果是**乘法叠加**的，不是加法。假设：
- 入口缩小 80%（从 1000 个 WorkItem → 200 个）
- 内部加速 30%（每个 WorkItem 少算 30% 的行）

总加速比 = (1000/200) × (1/0.7) ≈ **7.14x**，不是 1.3x + 5x = 6.3x，也不是各自单独的比例。

**要求**：在方案正文末尾加一段「与推荐系统协同的预期总收益分析」。

## 四、值得肯定的亮点

不是只给挑刺，下面这些确实做得好：

**1. 保守剪枝策略选择正确**

你选择了「系统偏小 → 只淘汰超上限」的保守方向，而不是试图兼顾上下限——这个判断是对的。误杀（False Negative）对于变压器报价场景是不可接受的，保守策略是唯一正确的选择。

**2. 数据依赖分析表做得清晰**

```
Phase 1（半径+周长）→ P0, PK
Phase 2（漏抗数据） → UK
Phase 3（散热数据） → 温升
```

这张表说明了你在读代码时真正跟进了数据流，而不是读个大概。这是本学期最好的工程习惯之一。

**3. 第三类「最坏情况总计算量不变」的底线承诺**

加判定前的计算顺序调整，不新增任何计算量——这是一个负责任的工程承诺。验收也直接：跑历史方案，看结果是否一致。

**4. 线规粗步进的保守判断**

你给出了粗扫通过率三种场景的定量分析，并得出「先加埋点收集数据，再决定是否实施」的结论——比起贸然上代码，这个决定成熟。
