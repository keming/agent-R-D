# 知微·大仪智能体 — 产品方案

> **产品名称**：知微·大仪智能体  
> **项目名称**：面向大型仪器的多智能体协同管控平台研究与实现  
> **编制日期**：2025年7月  
> **版 本**：V1.0

---

## 1. 项目概述

### 1.1 背景

杭州电子科技大学自2019年起承担浙江省大型仪器物联网传感器研发、运维及数据解析工作，已在全省226个高校院所安装近13000台物联网传感器，积累近5年的连续运行数据。团队提出了基于深度学习的科学仪器运行状态识别模型（CNN/Attention-LSTM），已获授权5项发明专利、2项软件著作权，制定1项团体标准。

然而，杭电本校目前尚未形成面向自身管理需求的大仪智能管控工具——海量数据汇入省平台后，本校实验室与设备管理处缺乏专用的数据分析和决策支持系统。本项目正是为解决这一缺口而设立。

### 1.2 产品定位

**知微·大仪智能体**是一个面向杭电实验室与设备管理处的智能管理平台，基于已有5年物联网传感器数据和深度学习故障预测模型，以多Agent协同架构实现大型仪器的**智能监控、风险预警、绩效评价、购置决策支持**四大核心能力。

> "知微"——见微知著，从细微的传感器信号变化中预知仪器故障。

### 1.3 目标用户

| 用户角色 | 核心诉求 | 使用场景 |
|---|---|---|
| 实验室与设备管理处（校级） | 全校大仪监管、绩效考评、购置审批、健康保试点 | 日常监控、周月报、决策会 |
| 校领导 | 仪器资产运行概览、预算决策依据 | 汇报会、审批 |
| （远期）各学院实验中心 | 本院仪器使用分析、开放共享管理 | Phase 2 开放 |

## 2. 核心功能设计

系统采用四层架构，由四个协同工作的 Agent 构成：

```
┌─────────────────────────────────────────────────┐
│                  知微·大仪智能体                   │
│                                                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐       │
│  │ 知微-看板  │  │ 知微-预警  │  │ 知微-决策  │       │
│  │  Agent   │  │  Agent   │  │  Agent   │       │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘       │
│       │              │              │              │
│  ┌────┴──────────────┴──────────────┴─────┐      │
│  │         知微-数据 Agent                 │      │
│  │   (数据接入 + 模型推理 + 画像计算)       │      │
│  └────────────────┬────────────────────────┘      │
│                   │                               │
│           省平台 IoT 数据库（5年数据）              │
└─────────────────────────────────────────────────┘
```

### 2.1 知微·看板 Agent — 管理驾驶舱

实验室处每天打开系统看到的"第一屏"，只回答三个问题：

#### 2.1.1 三大核心指标卡

| 指标 | 计算口径 | 阈值预警 |
|---|---|---|
| **闲置率 > 30% 仪器数** | 月使用机时 < 30% 额定机时 | ≥5 台标红 |
| **高风险故障仪器数** | 健康指数 < 60 分的仪器 | ≥3 台标红 |
| **当月使用率环比** | (本月均值 − 上月均值) / 上月均值 | 下降 > 10% 标绿 |

#### 2.1.2 仪器总览视图

以表格 + 热力图方式展示全校大仪核心指标：

| 学院 | 仪器名称 | 当月使用率 | 健康指数 | 闲置天数 | 操作 |
|---|---|---|---|---|---|
| 电子信息学院 | SEM扫描电镜 | 78% | 85 | 3 | 详情 |
| 材料与环境学院 | XRD衍射仪 | 22% 🔴 | 92 | 45 | 详情 |
| 计算机学院 | GPU集群 | 95% | 72 ⚠️ | 0 | 详情 |

- 支持按学院、按仪器类型、按健康状态筛选
- 支持导出 Excel/PDF 报表

#### 2.1.3 趋势图

- 近12个月全校大仪使用率趋势曲线
- 各学院使用率排行饼图/柱状图
- 故障报警次数月度统计

### 2.2 知微·预警 Agent — 智能预警与健康保

这是产品**最核心的技术创新点**，直接复用团队已有的 CNN/Attention-LSTM 发明专利成果。

#### 2.2.1 健康指数模型

每台仪器每日自动计算 **健康指数（0~100分）**：

| 分值区间 | 状态 | 管理动作 |
|---|---|---|
| 85~100 | 健康 | 正常维护 |
| 70~84 | 关注 | 列入观察，提醒每周检查 |
| 50~69 | 需检修 | 通知管理员安排检修 |
| 0~49 | 危险 | 建议立即停机维修 |

计算因子：
- **历史故障频率**（过去12个月维修记录）
- **实时运行参数偏移**（电流、振动、温度与基线偏差）
- **使用强度**（连续运行时长、负载率）
- **同类仪器横向对比**（校内同型号的健康基线）

#### 2.2.2 故障提前预警

基于 Attention-LSTM 模型，对每台仪器**提前7天**预测故障概率：

- 预警分级：蓝（关注）/ 黄（提醒）/ 红（告警）
- 多渠道推送：钉钉/邮件/系统内通知
- 预警详情：仪器名称、学院位置、预测故障类型、建议措施

#### 2.2.3 健康保试点对接

- 为每台大仪输出健康评级报告
- 保险公司根据健康指数确定保费折扣
- 支持批量导出保险投保清单

---

### 2.3 知微·决策 Agent — 绩效评价与购置决策

这是实验室处**最有痛点的功能**——每年预算分配和绩效考核。

#### 2.3.1 学院绩效评价

自动计算各学院大仪管理绩效，支持年度/季度考核：

| 评价维度 | 权重 | 计算方式 |
|---|---|---|
| 平均使用率 | 35% | 学院所有大仪月均使用率均值 |
| 开放共享率 | 25% | 对外共享机时 / 总机时 |
| 故障率 | 20% | 年维修次数 / 仪器台数（反向） |
| 产出成果 | 20% | 支撑的论文、专利、项目数量 |

- 学院排名 → 自动生成考核报告
- 与上年度对比 → 进步/退步标注
- 支持导出给实验室处的正式报告

#### 2.3.2 购置决策辅助

实验室处最头痛的问题——"这个预算该不该批"？

系统提供 **购置建议报告**，包含：

1. **校内同类仪器检索**：名称模糊匹配，列出校内同类型/同型号仪器清单
2. **使用率分析**：现有同类仪器的历史平均使用率
3. **饱和度预测**：如果新增一台，全校同类仪器的预期利用率变化
4. **建议结论**：推荐购买 / 不建议购买 / 建议调剂现有仪器

**示例输出**：

```
申购仪器：场发射扫描电镜（SEM）
申购学院：材料与环境学院
预算：380万元

校内同类仪器：3台
  - 电子信息学院 SEM（使用率 78%）
  - 理学院 SEM（使用率 62%）
  - 材环学院 SEM（使用率 22%，闲置中）

分析结论：
  ⚠️ 不建议购置
  理由：材环学院已有1台SEM闲置率78%，建议先评估该台仪器的共享使用方案，
        若利用率仍无法提升，再考虑采购决策。
```

#### 2.3.3 开放策略建议

基于忙闲时段分析模型，为每台仪器推荐最优开放方案：

- "这台仪器周二至周四下午最空闲，建议开放对外共享"
- "该仪器晚间（18:00-22:00）使用率仅5%，可开展夜间共享服务"

---

### 2.4 知微·数据 Agent — 数据底座

作为底层支撑Agent，统一封装数据接入、模型推理、画像计算。

#### 2.4.1 数据接入

| 数据源 | 内容 | 更新频率 |
|---|---|---|
| 省平台IoT传感器 | 运行状态、电流、振动、温度等 | 实时/分钟级 |
| 省平台静态库 | 仪器型号、购置日期、学院归属等 | 日级 |
| 维修记录 | 故障时间、维修内容、费用 | 事件驱动 |
| 预约系统 | 预约/使用记录、排队情况 | 实时 |

#### 2.4.2 大仪画像计算

对每台仪器自动生成多维度画像，每24小时更新一次：

| 画像维度 | 指标示例 |
|---|---|
| 基本属性 | 型号、购置年份、原值、所属学院 |
| 运行画像 | 月均使用率、累计运行时长、忙闲时段分布 |
| 健康画像 | 健康指数、维修次数、故障间隔 |
| 贡献画像 | 支撑论文数、支撑项目数、共享收益 |
| 效益画像 | 使用率效益比、投入产出评分 |

## 3. 技术架构

### 3.1 总体架构

```
┌─────────────────────────────────────────────────────────┐
│                   知微·大仪智能体                         │
│                                                         │
│  ┌──────────────── UI 层 ────────────────┐              │
│  │  知微·看板（React / Vue + ECharts）    │              │
│  └────────────────┬────────────────────────┘              │
│                   │ REST / WebSocket                       │
│  ┌────────────────┴────────────────────────┐              │
│  │            API 网关（FastAPI）            │              │
│  └──────┬──────────┬───────────┬────────────┘              │
│         │          │           │                           │
│  ┌──────┴──┐ ┌─────┴─────┐ ┌──┴─────────┐                │
│  │ 预警模块│ │ 评价决策  │ │ 看板统计  │                │
│  │(模型推理)│ │ (规则引擎) │ │ (聚合查询) │                │
│  └──────┬──┘ └─────┬─────┘ └──┬─────────┘                │
│         │          │           │                           │
│  ┌──────┴──────────┴───────────┴────────┐                │
│  │          数据接入层                    │                │
│  │  (省平台API + 定时同步 + 数据清洗)     │                │
│  └────────────────┬───────────────────────┘                │
│                   │                                        │
│  ┌────────────────┴───────────────────────┐                │
│  │          杭电校内数据库                  │                │
│  │  (PostgreSQL + TimescaleDB 时序扩展)    │                │
│  └─────────────────────────────────────────┘                │
└─────────────────────────────────────────────────────────┘
```

### 3.2 关键技术选型

| 层次 | 技术选项 | 选型理由 |
|---|---|---|
| 后端框架 | FastAPI (Python 3.11+) | 异步性能好，原生支持 WebSocket 推送 |
| 时序数据库 | PostgreSQL + TimescaleDB | 复用团队熟悉的 PostgreSQL 生态，TimescaleDB 天然支持时序查询 |
| 模型推理 | ONNX Runtime 或 Triton Inference Server | 将已有 PyTorch 模型导出为 ONNX，推理延迟 < 50ms |
| 前端 | React + ECharts / AntV | 看板类和图表展示需求为主，不需要重型框架 |
| 任务调度 | APScheduler + Celery | 定时画像计算、模型推理、数据同步 |
| 推送通道 | 钉钉机器人 Webhook | 杭电使用钉钉办公 |
| 部署 | 杭电校内服务器 (Docker Compose) | 数据不出校，满足安全要求 |

### 3.3 数据流

```
省平台IoT传感器（实时数据流）
    ↓
知微·数据Agent（定时 pull，每分钟拉取增量）
    ↓
数据清洗 & 特征工程
    ↓
┌─────────────────────────────────────┐
│ 杭电校内时序数据库                    │
│ (5年历史 + 实时增量)                 │
└──────┬──────────────────────────────┘
       │
       ├──→ 知微·预警Agent（每日模型推理）→ 健康指数 + 故障预测
       ├──→ 知微·看板Agent（按需聚合查询）→ 仪表盘指标
       └──→ 知微·决策Agent（定时+事件触发）→ 绩效评价/购置建议
```

## 4. 实施计划

### Phase 1（第1~2个月）—— 核心能力上线

| 里程碑 | 交付物 | 说明 |
|---|---|---|
| **M1** 数据链路打通 | 省平台 → 校内数据库实时同步 | 搭建数据管道，确认数据质量 |
| **M2** 模型部署 | 故障预测模型 ONNX 服务化 | 包装已有专利模型为 API |
| **M3** 看板 MVP | 知微·看板 v1 上线 | 三大核心指标 + 仪器总览表 |

**M3 为 Phase 1 终点**——实验室处能看到：高风险仪器列表、使用率排行、闲置仪器榜单。

### Phase 2（第3~4个月）—— 预警与决策

| 里程碑 | 交付物 |
|---|---|
| **M4** 智能预警上线 | 健康指数 + 故障预警推送（钉钉） |
| **M5** 绩效评价上线 | 学院绩效排名 + 自动报表 |
| **M6** 购置决策上线 | 购置建议报告生成 |

### Phase 3（第5~6个月）—— 完善与健康保对接

| 里程碑 | 交付物 |
|---|---|
| **M7** 健康保对接 | 健康评级报告导出 |
| **M8** 系统优化 | 性能调优、用户体验打磨 |
| **M9** 正式交付 | 部署文档、操作手册、运维培训 |

## 6. 与省平台的关系

```
┌─────────────────────┐       ┌──────────────────────┐
│  省平台 IoT 数据库   │  ←→   │  知微·大仪智能体     │
│  （226个高校院所）    │       │  （杭电专用）        │
│                     │       │                      │
│  功能：全省监管      │       │  功能：杭电精细化管理  │
│  用户：省科技厅      │       │  用户：杭电实验室处   │
│  粒度：地市/校级别   │       │  粒度：每台仪器/学院  │
└─────────────────────┘       └──────────────────────┘
```

**关系定位**：省平台是数据源，知微是增值应用层。省平台解决"有没有数据"，知微解决"数据怎么用出价值"。

- 数据层面：单向同步，知微从省平台拉取杭电数据，不上行写入
- 功能层面：互为补充，省平台看不到学院级绩效和预测，知微做精做深
- 推广层面：知微在杭电跑通后可作为示范应用对接全省其他高校
