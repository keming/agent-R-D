## 1. 文档概览

### 1.1 产品定位

　　知微·大仪智能体不是另一个大型仪器管理系统，而是在基理科技Genee系统和浙江省大仪开放共享平台之上叠加的智能分析层。它不做预约、计费、用户权限等Genee已经做好的功能，而是专注于回答Genee回答不了的三个问题：哪台仪器快要坏了？哪个学院的仪器绩效最差？这台仪器该不该买？

### 1.2 核心能力

　　本产品以多智能体协同架构提供四大核心能力：智能监控（看板Agent）、风险预警（预警Agent）、绩效评价与决策支持（决策Agent）、数据底座（数据Agent）。

### 1.3 与现有系统的边界

　　本产品与省平台和Genee系统形成互补关系：数据单向从省平台拉取，不上行写入；功能层与Genee互补，不替代其预约计费流程；消息推送通过杭电现有钉钉通道完成；用户认证复用杭电统一身份认证。

## 2. Phase 1：DISCOVER — 问题发现与假设验证

### 2.1 问题陈述

　　杭州电子科技大学自2019年起已在全省226个高校院所部署近13000台物联网传感器，积累近5年的连续运行数据，团队已获5项发明专利和2项软件著作权。然而，杭电本校实验室与设备管理处仍然面临以下困境：

| 问题 | 现状 | 量化损失 |
|---|---|---|
| 仪器使用情况看不清 | 依赖省平台通用报表，粒度只能到校级别 | 无法识别闲置仪器，年均仪器重复购置浪费预估数百万元级 |
| 故障预警靠人工 | 仪器坏了才知道，维修周期长 | 每台大仪年均故障停机损失约5~15个工作日 |
| 绩效评价靠填表 | 各学院每季度手工填报Excel | 数据滞后1~2个月，不可信、不可比 |
| 购置决策靠经验 | 缺乏历史数据支撑，"隔壁买了所以我们也买" | 杭电大仪年均新增投资中大比例存在重复购置风险 |

### 2.2 利益相关方与场景

　　实验室与设备管理处的核心场景是日常监控、周月报汇总和决策会汇报。校领导的使用场景主要是预算审批和年度考核。各学院实验中心（远期）的核心场景是本学院仪器使用分析和开放共享管理。

### 2.3 多视角发散

　　从产品经理视角出发，核心机会在于填补省平台和Genee之间的分析空白——省平台做监管，Genee做流程，两者都没有做智能分析。从设计师视角出发，关键在于以管理驾驶舱的极简交互让实验室处在10秒内掌握全校大仪核心状态。从工程师视角出发，关键约束是已有5年传感器数据和深度学习模型可以直接复用，不需要从零开始。

　　综合三个视角，最终锁定五个核心方向：健康指数计算、故障预测预警、学院绩效自动评价、购置决策辅助、健康保试点对接。

### 2.5 假设优先级矩阵

　　按影响力和不确定性两个维度排序：

| 优先级 | 假设 | 验证方式 |
|---|---|---|
| 🔴 高 | 省平台数据接口稳定可用 | 搭建数据管道后验证7天 |
| 🔴 高 | Attention-LSTM模型在杭电数据精度达标 | 用杭电5年数据做回测 |
| 🔴 高 | 实验室处愿意为分析结果打开第二个系统 | 2周内出看板MVP，实测使用频率 |
| 🟡 中 | 购置建议报告被采纳为审批依据 | 与实验室处做一次模拟决策会 |
| 🟡 中 | 在读学生能在6个月内交付 | 拆分为3个Phase，逐个里程碑确认 |
| 🟢 低 | 健康保政策落地时机 | 先做健康指数，政策落地时直接对接 |

### 2.6 低成本实验设计

| 实验 | 对应假设 | 方法 | 成本 |
|---|---|---|---|
| 数据管道可行性验证 | 省平台接口稳定性 | 搭建数据同步管道，运行7天 | 1人周 |
| 模型精度回测 | 模型在杭电数据上达标 | 用杭电5年历史数据跑一次离线推理 | 1人天 |
| 看板MVP实测 | 实验室处使用意愿 | 2周内出看板，请实验室处处长用一次 | 2人周 |

## 3. Phase 2：RESEARCH — 用户研究与竞品格局

### 3.1 用户画像

#### 画像一：实验室处处长（校级管理者）

| 维度 | 描述 |
|---|---|
| Job To Be Done | 每月向校领导汇报全校大仪使用绩效，每年审批数千万的仪器购置预算 |
| 三个痛点 | ① 绩效数据靠各学院填Excel，不敢直接拿去做考核；② 购置审批没有数据依据，批了怕浪费、不批怕影响科研；③ 仪器坏了才知道，维修经费无法提前预算 |
| 三个收益 | ① 自动生成的绩效报表可以直接拿去开会；② 购置建议报告让审批变得有理有据；③ 故障预警让维修预算可预期 |
| 反直觉洞察 | 处长并不需要一个"更好用的Genee"——他需要的不是一个预约系统，而是一个决策支持系统 |

#### 画像二：实验室管理科员（日常执行者）

| 维度 | 描述 |
|---|---|
| Job To Be Done | 每天监控全校大仪运行状态，每周汇总异常情况 |
| 三个痛点 | ① 现在要在省平台、Genee、Excel之间来回切换；② 异常情况靠经验判断，没有量化标准；③ 出报表耗时耗力 |
| 三个收益 | ① 一个看板看到所有核心指标；② 系统自动标红异常仪器，不用自己盯；③ 报表一键导出 |
| 反直觉洞察 | 科员最大的痛苦不是"没有数据"，而是"太多分散的数据" |

#### 画像三：校领导（决策者）

| 维度 | 描述 |
|---|---|
| Job To Be Done | 审批仪器购置预算，评估学院大仪管理绩效 |
| 三个痛点 | ① 预算申报材料缺乏横向对比数据；② 学院绩效评价标准不统一；③ 不清楚本校大仪与省内同类高校的对比 |
| 三个收益 | ① 每份购置申请附带数据对比报告；② 学院绩效排名一目了然；③ 横向对标数据辅助决策 |
| 反直觉洞察 | 校领导根本不会打开另一个系统——决策支持信息应该以报告形式出现在他的办公桌上 |

### 3.2 Job Stories

- 当我要审批仪器购置预算时，我想要看到校内同类仪器的使用率数据，以便判断是否真的需要新增。
- 当我要准备全校大仪器绩效汇报时，我想要一键生成各学院排名报表，以便直接拿去开会。
- 当某台仪器运行参数偏离基线时，我想要收到预警通知，以便在故障发生前安排检修。
- 当我要评估健康保试点可行性时，我想要每台大仪的健康指数评级，以便与保险公司对接。
- 当学院实验中心主任问我"我们院仪器用得怎么样"时，我想要本院仪器的分析报告，以便做管理改进。
- 当我要制定下学期开放共享政策时，我想要各仪器的忙闲时段分布，以便合理定价。
- 当省科技厅来检查大仪开放共享工作时，我想要导出完整的绩效数据，以便应对考核。

### 3.3 竞品分析

　　本产品的竞品格局已在独立调研报告中详细分析，此处只引用核心结论。完整的竞争格局分析见附录B。

| 竞品类别 | 代表厂商 | 与知微的关系 |
|---|---|---|
| 大型仪器管理系统 | 基理科技（Genee）——覆盖清华、北大、浙大等200+高校 | 互补：知微不做预约计费，做Genee没有的健康指数和故障预测 |
| 政府资产管理 | 久其软件——政府教育资产管理综合方案商 | 不直接竞争：久其在大仪领域只是产品线的极小部分 |
| 实验室物联网 | 能迪科技（Cleos）——面向生物/医疗实验室 | 场景不同：目标用户是实验室安全运维，非大仪共享管理 |
| 课题组级工具 | LABManagement、iLabPlus、ElabHost | 不在同一维度：面向单个课题组，非全校级 |

　　知微的核心竞争壁垒在于：拥有5年全省IoT传感器连续运行数据（竞品不可能拿到）、5项深度学习故障预测发明专利（已授权）、与省平台的数据直连通道（团队就是省平台建设方）。

## 4. Phase 3：STRATEGIZE — 价值主张与产品战略

### 4.1 价值主张画布

| 部分 | 内容 |
|---|---|
| Who（目标用户） | 杭电实验室与设备管理处（校级管理者） |

## 5. Phase 4：MEASURE — 北极星指标与OKR

### 5.1 北极星指标

　　本产品的游戏类型属于**生产力型（Productivity Game）**——帮助实验室处更快、更准地完成管理和决策任务。

**北极星指标：实验室处每周工作例会引用知微数据的次数**

　　这一指标直接衡量产品是否真正嵌入管理决策流程——引用次数越多，说明产品越不可或缺。

| 输入指标 | 说明 |
|---|---|
| 月活跃用户数 | 实验室处多少人在使用 |
| 故障预警准确率 | 模型预测准不准直接决定信任度 |
| 绩效报表导出次数 | 有没有被实际用于考核场景 |
| 购置建议被采纳率 | 决策建议有没有真正影响审批结果 |

### 5.2 OKR

#### Objective 1：建立实验室处对知微看板的日常使用习惯

| Key Result | 目标值 |

## 7. 附录A：技术架构设计

### 7.1 总体架构

　　本产品采用四层架构，由四个协同工作的Agent构成。底层为数据接入层，通过省平台API定时同步杭电大仪数据到校内数据库；中间层为预警模块、决策模块和看板统计模块，分别对应三个业务Agent；顶层为UI层，提供管理驾驶舱看板。

### 7.2 数据流

　　省平台IoT传感器采集的实时运行数据通过数据接入层定时同步至杭电校内时序数据库。预警Agent每日从数据库读取最新数据运行模型推理，产出健康指数和故障预测结果。看板Agent按需从数据库聚合查询，提供仪表盘指标。决策Agent定时或事件触发，计算绩效评价和购置建议。

### 7.3 关键技术选型

| 层次 | 技术选项 | 选型理由 |
|---|---|---|
| 后端框架 | FastAPI（Python 3.11+） | 异步性能好，原生支持WebSocket推送 |
| 时序数据库 | PostgreSQL + TimescaleDB | 复用团队熟悉的技术栈 |
| 模型推理 | ONNX Runtime | 轻量级，推理延迟<50ms |
| 前端 | React + ECharts | 看板类和图表展示需求为主 |
| 任务调度 | APScheduler + Celery | 定时计算和同步 |
| 推送通道 | 钉钉机器人Webhook | 杭电办公平台 |
| 部署 | 杭电校内服务器 + Docker Compose | 数据不出校 |

### 7.4 大仪画像数据模型

　　每台仪器自动生成5个维度画像，每24小时更新一次：基本属性（型号、购置年份、原值、所属学院）、运行画像（月均使用率、累计运行时长、忙闲时段分布）、健康画像（健康指数、维修次数、故障间隔）、贡献画像（支撑论文数、支撑项目数）、效益画像（使用率效益比、投入产出评分）。

### 7.5 健康指数计算模型

　　健康指数为0~100分，每天计算一次。85分以上为健康，70~84分为关注，50~69分为需检修，49分以下为危险。计算因子包括历史故障频率、实时运行参数偏移（电流、振动、温度与基线偏差）、使用强度（连续运行时长、负载率）、同类仪器横向对比。故障预警基于Attention-LSTM模型，提前7天预测故障概率，分蓝/黄/红三级推送。
