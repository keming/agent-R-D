## Phase 1：DISCOVER — 我们要解决什么问题？

### 问题陈述

**一句话**：资深专家大脑中 90% 的隐性知识在被问之前自己都不知道自己拥有，当前所有知识管理系统（Wiki / RAG / 知识图谱）都无法自主"开采"这些未被显化的知识；当专家离职，知识不可逆地流失。

**量化损失**：

| 损失维度 | 量化估算 | 来源基准 |
|---------|---------|---------|
| 知识流失率 | 资深工程师退休时带走 70–85% 的岗位关键判断经验 | US BLS 2029 预测 + Fenoglio 2022 |
| 新人不熟期 | 从头培养到独当一面需 18–36 个月 | 制造业/电力行业惯例 |
| 故障诊断效率差 | 资深 vs 初级工程师的故障定位时间差 5–10 倍 | 轨物科技现场经验 |
| 隐性 KM 投入 | 传统 KM 系统（Wiki/Confluence）的 ROI 极低 | 行业共识 |
| 直接年损失估算 | 单个专家离职导致团队效率下降 40–60%，持续 1–2 年 | PM 推断 |

### 三视角脑暴

| 视角 | 发散 | 收敛（Top 3） |
|------|------|-------------|
| **PM**（市场匹配） | ① 专家问答 SaaS ② 设备诊断 Agent ③ 师徒结对数字化 ④ 经验卡牌游戏 ⑤ 退休过渡知识审计 | ① 设备诊断蒸馏 Agent（最高频刚需）② 经验卡牌游戏（最有趣）③ 退休过渡审计（最紧迫） |
| **Designer**（用户体验） | ① AI 主动追问式对话 ② AR 实操记录 ③ 看板式知识卡片 ④ 语音笔记 + AI 整理 ⑤ 失败案例共享 | ① 主动追问对话（核心交互）② 知识卡片看板（存储+复用）③ 失败案例库 |
| **Engineer**（技术可行性） | ① LLM Agent + CBR 框架 ② 多 Agent 协作 ③ RAG + 向量库 ④ 场景化知识库格式 ⑤ 自验证回路 | ① LLM Agent + CBR（可行性最高）② 场景化知识库格式（关键创新）③ 自验证回路（差异化） |

**收敛后 Top 5 方案**：
1. **设备现场故障诊断蒸馏 Agent** — 在工程师排查故障时，AI 旁观察+主动追问，把诊断经验蒸馏入库
2. **经验卡牌游戏** — 把蒸馏包装成轻量游戏化交互，降低专家"被问"的抵触感
3. **退休过渡知识审计** — 针对即将退休的资深专家，系统性地启动蒸馏工作流
4. **场景化知识库** — 存储格式从"陈述性语法"转为"场景+决策+例外+溯源"
5. **自验证回路** — 专家修正 AI 输出时，AI 自动追问修正原因，沉淀为新规则

#### Persona 1：张工 — 资深电力设备诊断专家

| 维度 | 内容 |
|------|------|
| **角色** | 55 岁，东南某省电力公司高级工程师，35 年现场经验 |
| **JTBD** | "当我遇到罕见故障时，我想靠经验直觉快速定位，这样才不影响供电可靠性考核。" |

| **核心收益** | ① AI 替自己回答徒弟的重复问题 ② 自己的经验能被系统记住和复用 ③ 退休后知识还在公司 |
| **反直觉洞察** | **他不讨厌被提问，他讨厌被问蠢问题**——如果 AI 能问出"有水平"的问题，他其实愿意回答 |

#### Persona 2：李明 — 设备运维新人

| 维度 | 内容 |
|------|------|
| **角色** | 26 岁，本科毕业 2 年，工厂设备维护岗 |

| **核心痛点** | ① 师傅忙，不敢问 ② 查文档找不到匹配场景的答案 ③ 不知道"什么故障用什么排查思路" |
| **核心收益** | ① 有一个 "7x24 随时可问的虚拟师傅" ② 能看到类似案例的历史处理经验 ③ 能知道自己漏了什么排查步骤 |
| **反直觉洞察** | 他最大的敌人不是不知，而是**不知道自己不知道**——不知道自己漏掉了关键信号 |

| 维度 | 内容 |

| **反直觉洞察** | 他真正在意的不是"存了多少知识"，而是**"如果专家离职审计时能拿出东西给老板看"** |

### Job Stories

| # | Job Story |
|---|-----------|
| 1 | **When** 我遇到一个没见过但感觉以前类似的故障，**I want** AI 能问我"是不是和上次 #47 有点像"，**so that** 我不用自己翻记录凭记忆比对 |
| 2 | **When** 被 AI 追问时，**I want** 它问的问题不是百度就能搜到的，**so that** 我觉得它在配得上我的时间 |
| 3 | **When** 我修正了 AI 出的方案，**I want** AI 追问我修正原因，**so that** 我不需要单独花时间写文档 |
| 4 | **When** 新来的人问我一个蠢问题，**I want** AI 先替他挡掉一半，**so that** 我只需要回答"值得回答"的问题 |
| 5 | **When** 我做出一个关键判断，**I want** AI 记录下当时的上下文（设备型号、环境、数据），**so that** 以后这个判断能被精确复用而非模糊引用 |
| 6 | **When** 我要查一个以前处理过的案例，**I want** 按"相似的故障现象+设备型号"自动匹配，**so that** 不用等老同事回忆 |
| 7 | **When** 一年后的新人遇到某个故障，**I want** 他拿到的不只是"解决方案"，还有"当年老张为什么这么想"，**so that** 他能真正学到诊断思维 |

### 竞品分析

| 方案 | 类型 | 优势 | 局限 | 与我们的差异化 |
|------|------|------|------|-------------|
| **Confluence / 飞书文档** | 传统 KM | 基础设施成熟，团队已用 | 无人写、无人维护 | 我们不需要专家写——AI 问出来 |
| **RAG + 向量库（LangChain）** | AI KM | 检索+生成效果好 | 只能处理已存在的文档 | 我们产出的是原本不存在的知识 |
| **专家系统（传统）** | 规则引擎 | 精度高，解释性强 | 维护成本极高，专家访谈费时 | 我们用 LLM Agent 替代知识工程师 |
| **师徒制（人带人）** | 培训 | 效果最好，隐性知识靠实践传承 | 规模为 1:1，效率低 | 我们试图将 1:1 的效率提升到 1:N |
| **Guru / Stonly / 知识库 SaaS** | 轻量 KM | 好用的知识卡片/流程库 | 仍然是"写"的模式 | 我们核心差异是"蒸馏"而非"存储" |

### 客户旅程地图（专家张工视角）

| 阶段 | 触达 | 上手指引 | 首次蒸馏 | 持续使用 | 效果感知 |
|------|---------|---------|---------|---------|---------|
| **动作** | 王总推荐安装 | 看 3 分钟教程 | 处理一个故障，AI 全程旁观察+提问 | 每周 3-5 次故障处理，每次有提问 | 发现徒弟问自己的问题变少了 |
| **情绪曲线** | 怀疑->试试 | 还行->简单 | "别烦我" -> "这个问题有点意思" -> 满意 | 习惯->开始期待 AI 问的问题 | 意外发现 |
| **痛点** | 又多一个工具 | 怕浪费时间学 | AI 问了蠢问题 | AI 重复问同样的问题 | — |
| **机会** | 让王总亲自推荐 | 3 分钟内有"aha moment" | 必须前 3 次提问就有 1 个高水平问题 | 基于历史对话个性化提问 | 给专家看"经由你创造的新人提效数据" |

## Phase 4：MEASURE & ALIGN — 成功长什么样？

### 北极星指标

**游戏类型：Productivity Game（帮用户完成任务）**

**北极星指标：诊断场景的知识复用率**

> **定义**：当初级工程师遇到故障时，系统推荐的历史案例/蒸馏知识被实际采纳并帮助解决问题的比例

**为什么是这一个**：
- 它是统一指标（不是多个）
- 它衡量的是整个系统的产出质量（蒸馏得好不好 + 匹配得准不准 + 新人用得行不行）
- 它直接对应核心价值主张（"把专家知识变成帮新人解决问题的力量"）
- 它不符合任何收入指标（不选交易类），因为它真正反映产品本质

**输入指标（3-5 个）**：
1. **蒸馏覆盖率**：已被蒸馏的领域关键技能点 / 总的领域关键技能点
2. **主动追问高水平率**：专家评价为"有价值"的追问比例
3. **知识采纳率**：推荐的知识卡片/案例被用户点击且采纳的比例
4. **场景匹配召回率**：与当前故障场景匹配的历史案例被正确召回的比例

### OKR（3 组）

#### 组 1：知识蒸馏引擎（产品核心）

| 目标 | 关键结果 |
|------|---------|
| **O1：验证 AI 能自主蒸馏出有价值的隐性知识** | KR1.1：Concierge MVP 测试中，AI 追问被专家评为"有价值"的比例 >= 60% |
| | KR1.2：数据审计实验中，LLM 生成的追问 >= 6/10 被专家认可 |
| | KR1.3：完成 3 个真实故障场景的端到端蒸馏原型 |

#### 组 2：场景化知识库（知识存储与复用）

| 目标 | 关键结果 |
|------|---------|

| | KR2.2：场景匹配的召回率 >= 75%（top-3 结果） |
| | KR2.3：知识采纳率（推荐被用户确认有用）>= 50% |

## Phase 5：EXECUTE & SHIP — 把它做出来并保证质量

### Pre-Mortem（假设产品发布 14 天后失败）

#### Tigers（高概率 x 高影响 — 必须先验证）

| Tiger | 描述 | 验证方法 | Kill Criteria |
|-------|------|---------|-------------|
| **T1：专家反感被AI提问** | 实际使用 AI 追问时，专家觉得被打扰/被冒犯/浪费时间 | Concierge MVP 观察专家反应 + 事后访谈 | 3 次互动中有 2 次专家表示"不舒服"或中断对话 |
| **T2：AI提问质量低** | LLM 提出的问题被专家评为"毫无价值"或"网上搜得到" | Data Audit 方式让专家对 20 个问题打分 | < 50% 被评为"有价值" |
| **T3：企业不愿为"隐性的东西"付费** | 财务决策者认为"知识流失是未来的问题，不是今天的问题" | Landing Page + 5 家客户访谈 | < 2/5 表示"有兴趣"或"会预算" |
| **T4：蒸馏出的知识"正确但不实用"** | 知识被记录但新人用不上——格式不对或场景匹配不准 | MVP 阶段用 5 个真实故障验证新人是否能按建议做 | < 50% 的推荐被新人采纳 |

#### Paper Tigers（看起来危险但可控）

| Paper Tiger | 为什么可控 |
|-------------|-----------|
| **P1：LLM API 成本太高** | 初期客户数少，成本可控；蒸馏后的知识可缓存，每次故障不需要重新蒸馏 |
| **P2：场景适配需要太多手工调优** | 第一条线会重，但第二条标准化模板后就快；定制部分可收费 |
| **P3：竞品先做了** | 当前没有竞品做"蒸馏"方向；RAG/KM 玩家不会转型到这个方向（核心逻辑不同） |

#### Elephants（低概率但致命 — 需要 Plan B）

| Elephant | Plan B |
|----------|--------|
| **E1：大模型能力迭代方向变了（比如不再支持对话追问）** | 保持 Agent 框架独立于具体模型 API；预留本地模型（如通过 Ollama 部署） |
| **E2：关键合作专家离职或抵触** | 每客户至少培养 2 位专家参与，避免单点依赖 |
| **E3：数据安全/合规导致 LLM 不能在客户侧使用** | 支持私有化部署模式（纯本地模型+离线蒸馏） |

### Red Team（攻击 5 个关键假设）

| 假设 | 攻击问题 | 最便宜验证 | Kill Criteria |
|------|---------|-----------|-------------|
| 1. 专家愿意被 AI 提问 | "如果你修东西时一个 AI 不停地问你为什么这么做，你会不会想把机器砸了？" | 用真人扮演 AI，对 1 位专家做 30 分钟模拟 | 专家 3 次拒绝回答或表示烦躁 |
| 2. AI 能问出好问题 | "LLM 对工业领域的理解深度可能连关键词都猜不对，你能指望它问出专家觉得有水平的问题？" | 拿一个真实的故障工单让 GPT-4/DeepSeek 生成 5 个追问，让另一个领域专家打分 | 0/5 "有价值"评价 |
| 3. 场景化知识库能被检索到 | "你敢保证用的人输入的文字和场景描述，能匹配到专家当年建模的那个场景？" | 构建 20 张场景知识卡片，让 3 个新人写 10 个真实故障描述，测召回率 | 召回率 < 50% |
| 4. 企业会付费 | "现在的 CIO 被 RAG 忽悠过一次了，你凭什么让他们相信这次不一样？" | 把产品描述给 5 个 CIO 看，问"RAG 和我们有什么本质区别" | 3/5 认为"和 RAG 差不多" |
| 5. 蒸馏效率能规模 | "如果把一个专家的经验全蒸馏完要 3 个月，那他在这 3 个月里每天都在被问，他受得了？" | 模拟 10 个不同的故障场景，统计完成每个蒸馏需要的平均追问轮数 | 平均 > 15 轮/场景 |

### 用户故事（Top 8 按优先级）

| # | 用户故事 | 验收标准 |
|---|---------|---------|
| **US1** | **As 资深专家**, I want AI 在我处理故障时旁观察并偶尔提问题，So that 我不需要额外花时间写文档 | AC1: AI 能识别出我开始了故障排查（通过工单/操作） AC2: AI 的提问频率 <= 1 次/5 分钟 AC3: 提问内容和当前故障场景相关 |
| **US2** | **As 资深专家**, I want AI 问的问题是经过加工的而不是百度百科能回答的，So that 我觉得值得回答 | AC1: "高水平追问"比例 >= 70%（专家评价） AC2: AI 能引用领域特定术语而非通用表述 |
| **US3** | **As 资深专家**, I want 在我修正 AI 的方案后 AI 主动问"为什么这么改"，So that 我不需要再单独写反思 | AC1: 修正后 30 秒内自动触发追问 AC2: 追问的答案自动以场景化格式入库 |
| **US4** | **As 初级工程师**, I want 遇到未知故障时系统自动推荐最相似的历史案例，So that 我不需要自己翻记录或等师傅 | AC1: 输入故障现象后 5 秒内返回 top-3 案例 AC2: 匹配准确率 >= 75%（专家验证） |
| **US5** | **As 初级工程师**, I want 看到的不只是"怎么做"，还有"老张当年为什么这么想"，So that 我真正学到诊断思维 | AC1: 每个知识点包含"决策原因"字段 AC2: 知识卡片有"溯源"链接到原始对话记录 |
| **US6** | **As 知识管理负责人**, I want 看到各专家的"蒸馏覆盖率"仪表盘，So that 我能向上汇报知识沉淀进度 | AC1: 仪表盘显示"已蒸馏/总场景"比例 AC2: 支持按专家、场景、时间段筛选 |
| **US7** | **As 知识管理负责人**, I want 能追溯每个知识条的来源专家和场景，So that 出问题时能找到人核实 | AC1: 每条知识有 provenance 字段（专家+日期+故障单号） AC2: 支持按专家名的搜索过滤 |
| **US8** | **As 系统**, I want 对蒸馏出的知识做自一致性检查，So that 避免冲突或过时的知识污染库 | AC1: 新增知识若与已有知识冲突，触发人工审核 AC2: 标记超过 1 年未被引用的知识为"待确认" |

### 测试场景（BDD Given/When/Then）

| # | 场景 | Given | When | Then |
|---|------|-------|------|------|
| 1 | **Happy Path：蒸馏成功** | Given 专家正处理一个变压器过热故障，AI 检测到这是一个尚未被蒸馏的场景 | When 专家按照经验排除了三个可能原因后定位到问题 | Then AI 生成一张场景知识卡片（故障现象+排查路径+关键判断依据），专家确认后入库 |
| 2 | **Happy Path：知识复用** | Given 初级工程师遇到了一个和上次案例 #A47 相似的断路器跳闸故障 | When 他输入故障描述"三相不平衡+过流保护动作" | Then 系统在 top-3 推荐结果中返回 #A47 并显示匹配度 85% |
| 3 | **Edge Case：专家拒绝回答** | Given 专家正在处理一个时间压力很大的紧急故障 | When AI 发起了追问 | Then AI 自动延迟追问队列，等到专家完成紧急处理后（停机/恢复正常后）再发起 |
| 4 | **Edge Case：冲突知识** | Given 系统中已有知识"方案 A"描述了处理方法 X | When 另一个专家的蒸馏产生了与方法 X 冲突的方法 Y | Then 系统标记为冲突，触发人工审核流程，通知知识管理负责人仲裁 |
| 5 | **Edge Case：AI 问不到点子上** | Given AI 连续 3 次追问都被专家评为"没价值" | When AI 的自评价机制检测到"高水平率"低于阈值 | Then AI 自动切换追问策略（从"开放式提问"切换到"基于案例差异的对比提问"） |
| 6 | **Edge Case：离线环境** | Given 客户工厂网络条件差，无法实时调用云端 LLM API | When 蒸馏操作在本地环境触发 | Then 使用本地小模型（如 Qwen2.5-7B）生成追问，待网络恢复后同步到云端进行质量审核 |

## 附录：关键 PM 决策记录

| 决策 | 选项 | 选择 | 原因 |
|------|------|------|------|
| 知识存储格式 | ① 向量库 ② 场景化结构库 | **② 场景化结构库** | 向量库适合陈述性检索，场景化知识需要结构化匹配 |
| 追问触发机制 | ① 固定轮次 ② 事件驱动（修正/异常） | **② 事件驱动** | 减少对专家的打扰，只在"有料"时追问 |
| 首场景选择 | ① 设备故障诊断 ② 工艺参数优化 | **① 设备故障诊断** | 更直觉、更高频、专家经验更集中 |
| 部署模式 | ① 纯 SaaS ② 混合部署 | **② 混合部署** | 考虑客户数据安全顾虑和网络条件差异 |
| Agent 框架选择 | ① LangChain ② Hermes Agent ③ CrewAI | **Hermes Agent** | 已部署、可扩展、支持技能体系 + 子 Agent 并行 |

**Hermes Agent 选择理由**：
1. 当前对话环境中的工具体系已经就绪（terminal、execute_code、skill 管理）
2. 支持子 Agent 并行（可用于 CBR 检索、追问生成、冲突检测的并行编排）
3. 支持技能（Skill）体系——蒸馏出来的知识可以封装为 Hermes Skill
4. 可在本地/客户侧部署
