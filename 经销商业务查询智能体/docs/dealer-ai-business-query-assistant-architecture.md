# 经销商 AI 业务查询助手架构设计

日期：2026-06-11  
输入文档：[经销商AI业务查询助手产品方案.md](../经销商AI业务查询助手产品方案.md)

## 1. 一句话定位

经销商 AI 业务查询助手是嵌入晨龙经销商小程序的“业务查询编排器”：经销商用自然语言提出找设备、找配件、查主机订单、查配件订单的问题，系统将问题转成受权限保护的结构化查询，并返回可解释、可点击、可追踪的业务卡片。

关键判断：它不是开放聊天机器人，也不是替代现有业务系统的新交易入口。MVP 阶段应优先做“受控查询 + 推荐 + 页面衔接”，把下单、签收、审批等动作继续交给现有标准页面和权限流程。

## 2. 范围与假设

### 2.1 MVP 做什么

- AI 找设备：按型号、系列、产能、工况、联网监控等描述返回主机产品卡片。
- AI 找配件：按主机型号、配件用途、规格描述返回配件卡片。
- 主机订单进度查询：返回经销商权限范围内的主机订单进度卡片。
- 配件订单进度查询：返回经销商权限范围内的配件订单进度卡片。
- 结果卡片默认展示 5 条，最多展开前 50 条。
- 所有卡片必须带现有产品详情页或订单详情页跳转。
- 记录问题、意图、结果点击、反馈，用于试点评估。

### 2.2 MVP 暂不做什么

- 不做自动下单、自动审批、自动签收。
- 不做复杂经营分析、销售预测、自动营销。
- 不做跨系统流程编排。
- 不让大模型直接访问数据库或自由拼 SQL。
- 不让大模型直接决定订单状态、价格、权限或业务动作。

### 2.3 关键假设

- 经销商小程序已有登录态、经销商身份、产品详情页、订单详情页。
- 设备、配件、主机订单、配件订单已有结构化数据源或业务 API。
- 产品与配件适配关系至少能整理成结构化表；如果当前散落在说明文档或人工经验里，需要先做一轮数据治理。
- 试点期规模以 30-60 天验证为主，瓶颈首先是数据质量、召回准确率和权限边界，不是系统吞吐。

## 3. 质量属性目标

| 属性 | MVP 目标 | 设计含义 |
| --- | --- | --- |
| 准确性 | 常见设备选型、配件适配意图识别率 >= 80% | 必须建立黄金问题集和离线评测 |
| 可追溯性 | 每条推荐能说明来源字段或匹配依据 | 结果来自结构化数据和索引，不来自模型自由编造 |
| 安全性 | 经销商只能查自己权限范围内数据 | dealer_id 从登录态取得，不能由用户输入或模型生成 |
| 响应速度 | 常规查询 P95 <= 3 秒；含大模型解释 P95 <= 5 秒 | 意图识别、检索、重排要有超时与降级 |
| 可用性 | AI 失败时不影响现有小程序页面 | AI 入口旁路接入，详情和交易仍走原系统 |
| 可演进性 | 新增意图和工具不改前端主流程 | 后端采用“意图路由 + 工具注册 + 卡片协议” |
| 成本 | 单次查询模型调用可控 | 优先小模型分类、结构化检索，必要时才调用大模型 |

## 4. 架构选择

| 方案 | 描述 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| A. 规则/搜索型 BFF | 前端问题直接映射到固定接口和搜索条件 | 简单、成本低、可控 | 泛化弱，复杂表达理解差 | 可作为降级能力 |
| B. RAG 问答系统 | 把产品资料、订单资料切块入库，模型检索后回答 | 上手快，适合知识问答 | 订单和价格容易幻觉，权限风险高 | 不适合作为主路径 |
| C. 受控工具编排型 Agent | 大模型只做意图识别、槽位抽取、解释；业务查询由白名单工具完成 | 准确性、权限、审计和体验平衡最好 | 需要定义工具契约和评测集 | MVP 推荐 |
| D. 自主多 Agent 平台 | 多 Agent 自动规划、调用、反思、协作 | 长期扩展空间大 | 试点复杂度和不可控性过高 | 后续再评估 |

决策：MVP 采用 C，“受控工具编排型 Agent”。本质是确定性业务查询系统加一个自然语言入口，不是让模型自由操作业务系统。

边界说明：

- 现有业务系统仍是产品、价格、订单、权限的事实来源。
- 大模型不是事实来源，只是理解和表达能力组件。

## 7. 核心组件

### 7.1 小程序 AI 入口

职责：

- 承载 3 类入口：设备下单页、配件下单页、订单查询页。
- 根据入口传递初始上下文，例如当前页面、当前产品系列、当前订单类型。
- 展示统一卡片协议：产品卡片、配件卡片、订单进度卡片、澄清问题卡片、暂无结果卡片。
- 采集点击、展开、点赞/点踩、改搜等反馈。

建议：

- 输入框不要做成独立聊天孤岛，应放在业务页面上下文中。
- 设备下单页默认引导找设备；配件下单页默认引导找配件；订单页默认引导查订单，但仍允许跨意图识别。

### 7.2 AI 查询 BFF/API

职责：

- 校验登录态，解析 dealer_id、user_id、角色和入口来源。
- 请求限流、超时控制、会话 ID 生成。
- 屏蔽前端与具体模型、索引、业务接口的耦合。
- 统一返回卡片协议。

关键规则：

- dealer_id 只能来自后端可信登录态，不接受用户输入。
- 所有工具调用必须自动带上 dealer_id 和权限过滤条件。
- 任何模型输出都不能绕过工具层直接返回订单或价格。

### 7.3 意图路由与槽位抽取

职责：

- 将自然语言问题分类为：
  - find_device
  - find_accessory
  - query_host_order
  - query_part_order
  - clarification
  - unsupported
- 抽取槽位：
  - 设备：型号、系列、工况、材料、产能、联网需求、价格偏好。
  - 配件：主机型号、配件用途、规格、系列、是否常用/定制。
  - 订单：订单类型、客户名、时间范围、状态、是否最近、是否异常。
- 输出置信度和缺失槽位。

设计建议：

- MVP 可采用“小模型/LLM 分类 + 规则校验 + 少量正则词典”的混合方式。
- 置信度低或关键槽位缺失时，优先返回澄清问题，不要硬猜。
- 把 20-30 条常见问题扩展成黄金问题集，作为每次发布的 eval 门禁。

### 7.4 受控工具编排层

工具层是系统的安全边界。每个工具只做一类业务查询，输入输出都有 schema。

| 工具 | 输入 | 输出 | 数据来源 |
| --- | --- | --- | --- |
| product_search | dealer_id、型号、系列、工况、材料、产能、联网需求、分页 | 产品候选列表、匹配理由、详情页链接 | 产品库、产品索引 |
| accessory_match | dealer_id、主机型号、用途、规格、是否常用/定制、分页 | 配件候选列表、适配依据、详情页链接 | 配件库、适配关系 |
| host_order_search | dealer_id、客户、时间、状态、分页 | 主机订单进度列表、详情页链接 | 主机订单系统 |
| part_order_search | dealer_id、客户、时间、状态、分页 | 配件订单进度列表、详情页链接 | 配件订单系统 |

关键规则：

- 工具只读，不写业务数据。
- 工具不接受自由 SQL。
- 工具返回结构化结果和可解释字段，由响应组织层转成卡片。
- 工具失败要返回可识别错误类型：无权限、暂无结果、依赖超时、参数缺失、系统异常。

### 7.5 检索与索引层

AI 找设备、AI 找配件的质量主要取决于检索与数据治理。

推荐采用混合检索：

- 结构化过滤：系列、型号、价格区间、是否联网、产品状态。
- 全文检索：型号、别名、用途、规格、工况描述。
- 语义检索：经销商自然语言需求与产品描述、适配说明匹配。
- 重排：按业务权重、库存/可售状态、匹配字段、历史点击反馈排序。

MVP 技术选择：

- 如果现有系统已有搜索能力：优先复用现有搜索，补充同义词和业务词典。
- 如果需要新增：可用关系型数据库 + 全文索引起步；语义检索可用 pgvector 或独立向量库作为增强。
- 不建议试点期一开始引入复杂搜索集群，除非产品库规模和 QPS 已经超过关系型数据库可承受范围。

### 7.6 业务系统适配层

职责：

- 封装现有产品、配件、订单接口。
- 做字段映射、状态码翻译、错误归一化。
- 保护老系统，不让 AI 请求绕开原业务权限。

建议：

- 适配层返回“业务事实字段”，不要返回前端散乱字段。
- 订单状态解释使用白名单模板，例如“已发货，等待物流签收”，避免模型自由发挥。
- 如果老系统接口性能不稳定，增加短 TTL 缓存，但订单状态缓存要明确时效。

### 7.7 响应组织层

职责：

- 把工具返回结果组织成小程序卡片。
- 生成简短解释，例如推荐依据、订单进度说明、暂无结果建议。
- 控制展示数量：默认 5 条，展开最多 50 条。

关键规则：

- 价格、型号、订单状态等事实字段必须原样来自业务系统。
- 模型只能解释“为什么匹配”，不能生成不存在的产品、价格或订单状态。
- 每张卡片必须有稳定业务 ID 和详情页路由。

### 7.8 观测、反馈与评测

MVP 必须内置，否则 30-60 天试点无法判断成败。

采集指标：

- 意图分类准确率。
- 无结果率。
- 澄清率。
- 卡片点击率。
- 展开查看更多比例。
- 点赞/点踩反馈。
- P95/P99 响应时间。
- 模型调用次数、token 成本。
- 订单查询越权拦截数。

评测机制：

- 建立 20-30 条经销商常见问题作为 v1 黄金集。
- 每条问题标注期望意图、关键槽位、可接受结果类型。
- 每次改 prompt、词典、索引、重排规则前后跑离线 eval。
- 对差评样本进入人工复盘，沉淀同义词、适配规则或产品资料补充。

## 8. 关键数据流

### 8.1 AI 找设备

```text
1. 经销商在设备下单页输入：“用于中小规格棒料和管料及板材的锯切推荐”
2. 小程序提交问题、入口来源、会话 ID 到 AI 查询 BFF
3. BFF 从登录态解析 dealer_id 和 user_id
4. 意图路由识别为 find_device，抽取工况=锯切，材料=棒料/管料/板材，规格=中小规格
5. product_search 工具执行结构化过滤 + 全文/语义召回
6. 重排模块按匹配度、产品状态、业务优先级排序
7. 响应组织层生成前 5 条产品卡片和推荐依据
8. 小程序展示卡片；点击卡片进入现有产品详情页
9. 系统记录查询、候选、点击和反馈，用于后续评测
```

降级：

- 模型超时：使用关键词搜索返回候选。
- 无结果：提示可补充“材料、规格、产能、系列”等条件。
- 置信度低：反问“您更关注圆锯机、带锯床，还是某个具体系列？”

### 8.2 AI 找配件

```text
1. 经销商输入：“某型号有哪些常用配件”
2. 意图识别为 find_accessory，抽取主机型号和“常用配件”偏好
3. accessory_match 工具先查主机型号标准化映射
4. 查询适配关系表，召回常用配件、单台用量、规格
5. 如型号模糊，返回候选主机型号澄清卡片
6. 响应组织层返回配件卡片和“适配依据”
7. 点击进入现有配件详情页或配件下单页
```

关键点：

- 配件适配关系应优先来自结构化主机-配件关系，不建议只靠向量相似度。
- 如果没有适配关系，只能标注“可能相关”，不能标注“适配”。

### 8.3 订单进度查询

```text
1. 经销商输入：“最近的配件订单到哪了”
2. 意图识别为 query_part_order，时间范围=最近
3. BFF 注入 dealer_id，part_order_search 查询该经销商权限内订单
4. 订单系统返回订单编号、配件、状态、节点时间、详情页路由
5. 状态解释模板把内部状态码转成经销商易懂说明
6. 小程序展示订单进度卡片
```

关键点：

- 订单查询不能使用语义检索直接扫订单文本。
- 客户名、订单号等条件必须进入业务 API 查询。
- 无论用户怎么描述，都不能跨 dealer_id 查询。

## 9. 数据模型与存储选型

| 数据 | 访问形态 | 建议存储 | 一致性 | 说明 |
| --- | --- | --- | --- | --- |
| 产品主数据 | 按型号/系列/条件查询，卡片展示 | 现有产品库 + 产品索引 | 以业务库为准，索引最终一致 | 详情页字段来自业务库 |
| 配件主数据 | 按型号/用途/规格查询 | 现有配件库 + 配件索引 | 以业务库为准 | 与产品索引分开建模 |
| 主机-配件适配关系 | 按主机型号查配件，按配件反查主机 | 关系型表或图状关系表 | 强治理，变更可审计 | AI 找配件的核心数据 |
| 主机订单 | 按 dealer_id、客户、时间、状态查 | 现有订单系统 | 强一致读或准实时 | 不复制敏感订单全文到向量库 |
| 配件订单 | 按 dealer_id、客户、时间、状态查 | 现有订单系统 | 强一致读或准实时 | 同上 |
| 同义词/别名词典 | 查询改写、型号归一 | 配置表 | 发布一致 | 支持经销商口语 |
| AI 会话日志 | 排障、评测、产品分析 | 日志库/关系库 | 最终一致 | 脱敏存储 |
| 反馈数据 | 点击、点赞、点踩、无结果反馈 | 关系库/事件日志 | 最终一致 | 用于评测和重排 |
| 向量索引 | 语义召回 | pgvector/向量库 | 最终一致 | 只放产品/配件资料，不放敏感订单 |

## 10. API 与卡片协议

### 10.1 查询 API

```json
{
  "query": "某型号有哪些常用配件",
  "entry": "part_order_page | device_order_page | order_page",
  "session_id": "optional",
  "context": {
    "current_product_id": "optional",
    "current_order_type": "optional"
  }
}
```

服务端自动补充：

```json
{
  "dealer_id": "from_auth",
  "user_id": "from_auth",
  "roles": ["from_auth"]
}
```

### 10.2 统一响应

```json
{
  "answer_type": "product_cards | accessory_cards | order_cards | clarification | empty | unsupported",
  "intent": "find_accessory",
  "confidence": 0.91,
  "summary": "为您找到以下常用配件。",
  "cards": [],
  "trace_id": "req_20260611_xxx",
  "actions": [
    {
      "type": "show_more",
      "label": "查看更多"
    }
  ]
}
```

### 10.3 产品/配件卡片

```json
{
  "card_type": "product",
  "id": "product_123",
  "image_url": "https://...",
  "series": "高效系列",

  "match_reason": "匹配中小规格棒料、管料及板材锯切需求",
```

## 11. 安全与权限设计

核心原则：模型不可信、用户输入不可信、业务系统是事实来源。

必须落实：

- dealer_id、user_id、角色从登录态解析，不从自然语言抽取。
- 工具层统一注入权限过滤条件。
- 订单查询按 dealer_id、组织权限、客户可见范围过滤。
- 查询日志脱敏，避免记录完整手机号、地址、联系人等敏感字段。
- Prompt 中禁止暴露系统密钥、内部接口地址、权限规则细节。
- 对提示注入做基础防护：用户要求“忽略权限”“显示全部订单”等请求只能返回拒绝或澄清。
- 所有工具调用记录 trace_id、调用参数摘要、结果数量、耗时和错误码。
- 管理后台或配置表变更需要审计。

## 12. AI 质量控制

### 12.1 幻觉控制

- 产品、配件、价格、订单状态必须来自工具结果。
- 模型回答中引用的型号必须存在于结果集。
- 如果工具无结果，不能让模型编推荐。
- 推荐依据必须引用匹配字段，例如系列、型号、用途、适配关系、订单节点。

### 12.2 置信度策略

| 场景 | 策略 |
| --- | --- |
| 意图高置信且槽位充足 | 直接调用工具 |
| 意图明确但槽位缺失 | 调用工具时放宽条件，或返回澄清问题 |
| 多意图冲突 | 根据入口上下文优先，必要时澄清 |
| 模型低置信 | 降级关键词搜索或返回引导问题 |
| 工具无结果 | 返回暂无结果和可补充条件 |

### 12.3 Eval 门禁

建议建立 4 组评测：

- 意图识别 eval：输入问题 -> 期望意图。
- 槽位抽取 eval：输入问题 -> 期望型号、系列、时间、状态等。
- 检索召回 eval：输入问题 -> 期望候选产品/配件集合。
- 安全 eval：越权、提示注入、敏感信息请求必须拒绝或过滤。

试点初始黄金集：

- 设备问题 10 条。
- 配件问题 10 条。
- 主机订单问题 5 条。
- 配件订单问题 5 条。
- 安全/越权问题 5 条。

## 13. 部署形态

MVP 推荐模块化单体或小型服务集：

```text
dealer-ai-api
  ├─ auth adapter
  ├─ intent router
  ├─ tool orchestrator
  ├─ product tool
  ├─ accessory tool
  ├─ order tools
  ├─ response composer
  └─ telemetry

indexer-worker
  ├─ product sync
  ├─ accessory sync
  ├─ compatibility sync
  ├─ synonym build
  └─ vector/fulltext index build
```

理由：

- 试点阶段团队协作和发布复杂度比机器扩展更重要。
- 查询 API 与索引构建生命周期不同，建议拆成在线服务和离线/异步 worker。
- 工具内部可以模块化，等某个模块出现真实扩展压力后再拆服务。

## 14. 可观测性

每次请求至少记录：

- trace_id、session_id、entry、dealer_id_hash、user_id_hash。
- 原始问题脱敏文本。
- 意图、置信度、槽位。
- 调用工具、工具耗时、结果数量、错误码。
- 模型名称、token、耗时、成本。
- 返回卡片类型、卡片数量。
- 用户行为：点击、展开、反馈。

关键看板：

- 试点总请求数、活跃经销商数。
- 各意图占比。
- 无结果率和澄清率。
- 卡片点击率。
- P95/P99 延迟。
- 模型成本趋势。
- 低分反馈 Top 问题。
- 订单查询权限拦截事件。

## 15. 演进路线

### 15.1 MVP：30-60 天试点

- 打通 3 个小程序入口。
- 完成 4 类意图。
- 接入产品、配件、主机订单、配件订单只读查询。
- 建立产品/配件检索索引和适配关系表。
- 建立 30-35 条黄金 eval。
- 采集点击和反馈。

### 15.2 成长期：从“能查”到“更准”

- 扩展同义词、型号别名、经销商口语词典。
- 引入点击反馈重排。
- 引入更细的澄清策略。
- 增加“推荐理由可解释字段”。
- 对高频无结果问题做数据补齐。
- 将常见推荐路径沉淀成规则和模板。

### 15.3 成熟期：从查询助手到经销商服务智能体

- 增加经营分析、库存可用性、售后服务查询。
- 支持报价辅助、方案推荐，但仍需人确认。
- 与 CRM、售后、物流等系统形成更完整服务链路。
- 引入更严格的权限、审计、人审和自动化 eval。
- 在真实流量和组织边界需要时，再拆分独立搜索服务、Agent 网关或多 Agent 工作流。

## 16. 主要风险与反挑战

| 风险 | 第一个死点 | 应对 |
| --- | --- | --- |
| 配件适配数据不完整 | AI 找配件看起来会答，但实际错配 | 先治理主机-配件适配关系；无适配依据不标“适配” |
| 产品资料口径不统一 | 同一型号多个别名，召回不稳定 | 建型号归一、别名词典、产品状态字段 |
| 大模型幻觉 | 编造不存在型号、价格、订单状态 | 工具结果白名单，事实字段只来自业务系统 |
| 订单越权 | 用户用客户名试探其他经销商订单 | dealer_id 强制过滤，安全 eval，审计告警 |
| 响应慢 | LLM + 搜索 + 老系统 API 串行导致超时 | 并行工具、超时降级、缓存非敏感产品数据 |
| 无法证明价值 | 试点只有演示，没有指标闭环 | 从第一天记录点击、耗时、反馈和黄金集表现 |
| 成本漂移 | 每次都调用大模型做长回答 | 小模型分类、短 prompt、缓存、模板化解释 |

## 17. 建议补充的 ADR

### ADR-001：采用受控工具编排型 Agent，而不是开放聊天机器人

- 状态：建议采纳
- 背景：系统涉及产品价格、配件适配、订单状态和经销商权限。
- 决定：大模型负责意图、槽位、解释；业务事实由工具查询。
- 理由：降低幻觉、越权和不可审计风险。
- 代价：需要定义工具 schema、卡片协议和 eval。
- 触发升级信号：当业务查询超过 10 类且规则维护成本显著上升，再评估更通用的 Agent 工作流。

### ADR-002：订单数据不进入向量库

- 状态：建议采纳
- 背景：订单数据敏感且强权限相关。
- 决定：订单只通过业务 API 查询，不做语义向量检索。
- 理由：降低隐私、越权、数据过期风险。
- 代价：自然语言中的复杂订单描述需要更好的槽位抽取。
- 触发升级信号：如果订单查询语义需求明显增多，可先做受权限过滤的结构化搜索，不直接向量化敏感全文。

### ADR-003：试点阶段采用模块化单体 + 异步索引 worker

- 状态：建议采纳
- 背景：试点目标是验证价值，不是验证高并发平台。
- 决定：在线查询服务保持模块化单体，索引构建独立 worker。
- 理由：开发、部署、排障成本低。
- 代价：模块边界需要代码规范约束。
- 触发升级信号：某个工具的流量、发布频率、故障隔离需求明显独立时再拆服务。

## 18. 未决问题

这些问题会明显影响后续详细设计：

1. 现有产品、配件、订单系统是否已有稳定 API？如果没有，是直连数据库还是先补 API？
2. 产品和配件是否已有主数据标准，包括型号、系列、价格、图片、上下架状态？
3. 主机-配件适配关系当前是结构化表、Excel、说明书，还是人工经验？
4. 经销商权限模型是按 dealer_id、组织层级、区域，还是客户归属控制？
5. 订单状态码和进度节点是否已经统一？主机订单与配件订单是否同一套状态机？
6. 试点经销商数量、日查询量、产品/配件 SKU 规模是多少？
7. 小程序技术栈和现有页面路由协议是什么？
8. 部署环境是否允许调用外部大模型 API，还是必须私有化/本地化？

## 19. 下一步建议

1. 先做数据盘点：产品字段、配件字段、适配关系、订单字段、权限字段。
2. 定义卡片协议和 4 个工具 schema。
3. 准备 30-35 条黄金问题集，覆盖常见、模糊、无结果、越权问题。
4. 做一个端到端薄切片：设备下单页输入问题 -> product_search -> 产品卡片 -> 详情页跳转。
5. 再做配件适配，因为它最依赖数据治理，也是最能体现业务价值的能力。
6. 最后接订单查询，重点验证权限过滤和状态解释。
