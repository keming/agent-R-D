| 错误场景 | 严重度 | Rescue 策略 | 文档是否覆盖？ |
|----------|--------|------------|:---:|
| 用户问题意图无法识别 | HIGH | 回退到关键词搜索 + 提示用户换种问法 | ⚠️ 提到"暂无结果提示"，未详述 |

| 结果卡片跳转失败 | MEDIUM | 兜底展示产品ID/订单号供手动查询 | ❌ |

### 第 3 节 — Failure Modes Registry

| 失败模式 | 影响 | 触发条件 | 缓解 |
|----------|------|----------|------|
| AI 幻觉推荐不存在的配件 | 错选、退换货 | LLM 缺乏配件适配知识 | RAG + 数据约束，幻觉输出后过滤 |
| 高并发时查询慢 | 经销商放弃等待 | 促销/季末集中下单 | 结果缓存、异步预加载 |
| 意图识别偏移 | 查订单被识别为找产品 | 用户措辞模糊 | 多轮确认或歧义消解 UI |
| 订单状态数据延迟 | 显示"未发货"实际已发 | ERP 同步延迟 | 标注"数据更新时间" |
| 产品数据变更后搜索结果不更新 | 推荐已下架产品 | 索引未实时刷新 | 增量索引或 TTL 过期 |

### 关键架构决策

| 决策点 | 推荐 | 理由 | 代价 |
|--------|------|------|------|
| 意图识别方式 | LLM few-shot classification | 4 类意图，不需要训练专用模型 | 首次调用延迟～1s，成本按 token 计 |
| 产品搜索 | 向量检索 (embedding) + 关键词倒排混合 | 设备型号、系列是多维度模糊匹配 | 需要构建 embedding pipeline |
| 配件适配 | 结构化关系查询 + LLM 语义辅助 | 适配关系本质是结构化数据 | LLM 可能编造不存在的适配 |
| 订单查询 | 纯结构化 API 调用 | 订单状态查询不需要 AI | LLM 只做参数提取 |
| 会话管理 | 无状态（每条查询独立） | 当前场景不需要多轮对话 | 上下文依赖的问题无法处理 |
| 结果缓存 | TTL 5min 缓存常见问题结果 | 经销商问题重复率高 | 数据新鲜度 5min 延迟 |
| 部署方式 | 嵌入现有小程序后端 | 不引入新基础设施 | 受限现有架构能力 |

### 关键关切

**1. AI 幻觉风险 (CRITICAL)**

产品推荐场景下，LLM 可能推荐不存在或不匹配的产品/配件。必须做：
- 所有 LLM 输出经过结构化约束（function calling / structured output）
- 产品/配件查询结果必须从真实数据源检索，LLM 只做理解和排序
- 关键字段（价格、型号）永不通过 LLM 生成

**2. 数据依赖 (HIGH)**

- 意图识别依赖设备/配件数据的 embedding 质量
- 如果现有产品数据缺少结构化描述（工况、产能、联网能力），语义匹配效果会差
- **前置条件**: 梳理设备、配件、订单数据的关键字段，评估数据质量

**3. 可观测性 (MEDIUM)**

- 文档验收指标聚焦用户端，缺少系统端指标
- **建议补充**: P95 延迟、错误率、LLM token 消耗、缓存命中率

**4. 安全 / 多租户 (HIGH)**

- 经销商只能查看自己的订单
- 意图识别和查询需要携带经销商身份
- 防止提示注入（用户输入恶意 prompt 影响 LLM 行为）

### 测试策略

| 测试类型 | 覆盖目标 |
|----------|----------|
| 意图识别准确率 | 4 类意图 × 30 条典型问题 = 120 条测试集，目标 ≥90% |
| 设备推荐准确率 | Top-5 推荐中至少 1 条相关，目标 ≥80% |
| 配件适配正确率 | 推荐配件 100% 真实存在，≥80% 适配 |
| 订单查询正确性 | 100%（纯结构化查询） |
| Eval 门禁 | 每次 LLM prompt 变更跑全量 eval，准确率下降 >5% 则 Block |

| 维度 | 评分 | 说明 |

| 架构可行性 | 8/10 | 路线清晰，复杂度可控 |

## Phase 4 — Final Approval Gate

### 跨阶段主题

**主题 1: AI 风险覆盖缺失** — CEO、Design、Eng 三个阶段独立发现：

- CEO: 无 AI 幻觉、成本控制、质量漂移的考虑

- Eng: 无 AI 幻觉缓解策略、eval 门禁

> ⚠️ 三个维度独立确认的信号——**需要在开发前解决**。

**主题 2: 交互状态不完整** — Design + CEO 阶段发现：

- 只覆盖了"成功"态，缺少加载、空结果、错误、部分匹配

**主题 3: 系统可观测性缺失** — Eng 阶段发现：

- 只有用户端验收指标，无系统端（延迟、错误率、token 消耗、成本）

### User Challenge

**Challenge 1: AI 系统特有风险未覆盖** (来自 CEO + Design + Eng)

文档将 AI 查询助手描述为"自然语言→结果"的魔法盒子，但未说明：
- 当 AI 推荐错误产品/配件的降级策略
- 用户如何区分"AI 推荐"和"确定性数据"
- 系统如何检测 AI 输出质量退化
- Token 成本和延迟的用户体验影响

**推荐**: 在文档中新增"AI 系统风险与缓解"章节，至少覆盖幻觉、成本、评估门禁三项。
