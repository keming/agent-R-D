# 研发知识智能体产品优化方案

日期：2026-06-09  
定位：面向制造业研发负责人的研发降本增效 Agent 产品  
建议产品名：研发知识智能体 / Engineering Knowledge Agent  

## 一、产品定位

研发知识智能体不是传统文档管理系统，也不是普通知识库问答机器人，而是面向制造业研发部门的“研发知识与流程协同智能体”。

它服务的核心对象是研发负责人，目标是帮助其降低研发知识流失、重复设计、评审低效、变更失控和专家被反复打扰带来的隐性成本。

一句话定位：

> 面向设备制造企业研发部门，把技术文档、图纸、BOM、测试报告、故障案例和变更记录变成可追溯、可复用、可协同的研发知识智能体。

## 二、目标用户：研发负责人

### 2.1 研发负责人的核心痛点

| 痛点 | 表现 | 成本 |
| --- | --- | --- |
| 资料分散 | 图纸、BOM、测试报告、说明书、标准散落在多个系统 | 工程师找资料时间长 |
| 经验难复用 | 历史方案、踩坑记录、设计依据留在老员工脑子里 | 重复设计、重复验证 |
| 评审低效 | 设计评审前信息不完整，会上反复补背景 | 评审周期长、问题漏检 |
| 变更影响不透明 | 器件、参数、结构变化后，不知道影响哪些文档和测试 | 返工、漏改、质量风险 |
| 专家被反复打扰 | 高级工程师不断回答相同问题 | 高价值研发时间被稀释 |
| 文档不可追责 | 谁改了什么、为什么改、依据是什么不清楚 | 质量追溯和责任界定困难 |

### 2.2 产品为研发负责人交付的价值

- 降低研发资料查找和沟通成本。
- 提高历史设计方案复用率。
- 缩短新人上手周期。
- 提高设计评审质量。
- 降低变更遗漏风险。
- 形成可追溯的研发知识资产。

## 三、核心业务场景

### 场景 1：研发资料可信问答

研发人员可以围绕某个产品型号、器件、接口、协议、测试项进行自然语言提问。

示例问题：

- “SwitchGuard 支持哪些通讯协议？依据在哪份测试报告？”
- “上一版为什么没有选用国产 ADC？”
- “这个电源模块历史上出现过哪些故障？”

系统回答必须包含：

- 答案摘要
- 引用文档
- 文档版本
- 页码或段落位置
- 可信度提示
- 不确定信息说明

### 场景 2：历史方案复用

输入新项目需求后，Agent 自动查找历史相似项目、产品型号、BOM、测试报告和设计说明。

输出：

- 相似项目列表
- 可复用模块
- 设计差异
- 复用风险
- 推荐参考资料

### 场景 3：设计评审辅助

在设计评审前，Agent 自动读取需求文档、设计方案、BOM、测试记录和历史故障案例，生成评审材料。

输出：

- 设计评审问题清单
- 风险项列表
- 待确认事项
- 缺失文档
- 与历史项目的差异
- 建议补充测试项

### 场景 4：变更影响分析

当研发人员修改器件、结构、参数、协议、软件版本或工艺要求时，Agent 自动分析影响范围。

输出：

- 受影响文档
- 受影响 BOM 项
- 受影响测试项
- 受影响认证或标准
- 需要同步修改的说明书、交付文档和售后资料
- 建议通知人员

### 场景 5：售后问题回流研发

Agent 将现场故障、客户反馈、售后维修记录转化为研发改进建议。

输出：

- 问题归类
- 可能根因
- 涉及产品版本
- 涉及设计模块
- 建议改进项
- 是否进入下一版研发计划

### 场景 6：文档操作可追踪

这是研发负责人非常关心的管理能力，应作为核心功能加入，而不是后台附属功能。

系统需要记录每一次关键文档操作：

- 谁查看了文档
- 谁修改了文档
- 修改了哪些内容
- 修改前后差异是什么
- 修改原因是什么
- 引用了哪些依据
- 是否经过审批
- 是否触发了关联文档、BOM、测试项同步

可追踪能力的价值：

- 支持研发质量追溯。
- 支持版本责任界定。
- 支持设计变更审计。
- 支持知识贡献度统计。
- 避免“文档被改了但没人知道”。

## 四、产品功能模块

### 4.1 文档接入与治理

- 支持接入 Word、PDF、Excel、Markdown、图纸说明、测试报告、标准规范。
- 支持接入企业网盘、PLM、PDM、MES、飞书文档、企业微信文档。
- 自动识别产品型号、版本号、器件编号、测试项、接口协议等实体。
- 自动建立文档与产品、BOM、项目、故障案例之间的关联。

### 4.2 研发知识问答

- 支持按产品、项目、版本、部门限定问答范围。
- 答案必须带出处。
- 支持追问和对比。
- 支持“不确定”“资料缺失”“版本冲突”提示。

### 4.3 设计复用推荐

- 根据新需求匹配历史方案。
- 推荐可复用模块、器件、测试方案、结构方案。
- 标注复用风险和差异点。

### 4.4 设计评审 Agent

- 自动生成评审清单。
- 自动识别资料缺失。
- 自动发现历史类似问题。
- 自动生成会议纪要和待办。

### 4.5 变更影响分析

- 分析文档、BOM、测试、认证、说明书、售后资料之间的影响链。
- 生成变更影响报告。
- 支持变更审批流。

### 4.6 文档操作追踪与审计

核心能力包括：

- 文档访问日志
- 文档修改日志
- 版本差异对比
- 修改原因记录
- 审批记录
- 关联影响记录
- 操作人、时间、对象、动作、依据完整留痕

推荐形成“研发文档时间线”：

```
需求提出 → 方案修改 → BOM 变更 → 测试补充 → 评审通过 → 发布归档 → 售后反馈回流
```

### 4.7 研发负责人驾驶舱

面向研发负责人展示：

- 各产品线文档完整度
- 高风险变更数量
- 未闭环评审问题
- 高频问答主题
- 被复用最多的历史方案
- 专家被咨询热点
- 文档贡献和修改统计

## 五、MVP 范围

第一版不要做全功能平台，建议聚焦 4 个能力：

1. 研发资料可信问答
2. 历史方案复用
3. 设计评审辅助
4. 文档操作可追踪

暂不做：

- 复杂 PLM 替代
- 完整项目管理
- 自动生成全部研发文档
- 自动批准设计变更
- 深度 CAD 图纸解析

## 六、内部试点建议

轨物科技可以先用自己的研发资料做试点，选择一个产品线作为样板。

推荐试点对象：

- SwitchGuard
- SolarOps
- StoreMind
- 智能网关

试点资料：

- 产品需求文档
- 设计方案
- BOM
- 测试报告
- 用户手册
- 售后故障记录
- 项目交付文档
- 标准和认证资料

试点周期：60-90 天。

试点验收指标：

| 指标 | 目标 |
| --- | --- |
| 工程师找资料时间 | 降低 50% |
| 设计评审准备时间 | 降低 40% |
| 新人上手周期 | 缩短 30% |
| 重复咨询高级工程师问题 | 降低 30% |
| 关键文档操作追踪覆盖率 | 达到 90% |
| 每个项目自动沉淀知识条目 | 不少于 30 条 |

## 七、商业化路径

### 阶段 1：内部自用验证

先在轨物内部研发体系跑通，形成真实案例。

交付物：

- 内部产品线知识库
- 研发负责人驾驶舱
- 文档操作追踪日志
- 设计评审辅助报告
- 效率提升数据

### 阶段 2：面向设备制造客户试点

选择 2-3 家设备制造企业客户，优先找研发文档多、售后问题多、产品迭代快的客户。

收费方式：

- 试点实施费
- 年度订阅费
- 按产品线、用户数或文档量计费

### 阶段 3：形成行业模板

面向新能源电力设备、储能设备、开关柜、工业装备等行业形成模板。

模板内容：

- 文档分类模板
- 研发流程模板
- 评审清单模板
- 变更影响规则
- 常见故障知识包

### 阶段 4：扩展为企业工程智能体平台

从研发知识切入，逐步扩展到：

- 研发 Agent
- 售后 Agent
- 质量 Agent
- 生产工艺 Agent
- 设备运维 Agent

最终形成制造企业全生命周期知识闭环。

## 八、差异化定位

与普通知识库相比，轨物的差异化不在“能问答”，而在“懂制造业研发对象”。

| 普通知识库 | 研发知识智能体 |
| --- | --- |
| 管文档 | 管产品知识 |
| 回答文本问题 | 回答设计、测试、BOM、故障相关问题 |
| 只看单个文档 | 建立文档、产品、版本、BOM、测试、售后的关系 |
| 无追踪或弱追踪 | 全过程操作留痕和变更影响追踪 |
| 难证明 ROI | 可量化找资料时间、评审效率、复用率和变更风险 |

## 九、推荐产品表述

官网或销售材料可这样表达：

> 轨物研发知识智能体面向设备制造企业研发部门，连接技术文档、图纸、BOM、测试报告、故障案例和变更记录，帮助研发负责人沉淀工程知识、复用历史设计、提升评审效率，并实现关键文档操作全过程可追踪。

更短版本：

> 让研发资料从“能存”变成“能问、能复用、能追踪、能闭环”。

## 十、下一步行动

1. 选择轨物内部一个产品线作为试点。
2. 盘点该产品线全部研发资料和售后问题。
3. 定义文档分类、版本规则和操作追踪字段。
4. 做一个 60-90 天 MVP。
5. 用内部效率提升数据包装成第一个标杆案例。
6. 再对外拓展到设备制造企业研发部门。
